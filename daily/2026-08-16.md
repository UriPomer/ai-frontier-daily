## 1. DeepSeek V4-Pro：真正影响 Agent 体验的，越来越是“模型协议 + Harness”

- **标签**：`Agent` `Harness` `Coding` `LLM`
- **相关技术**：DeepSeek-V4-Pro、Claude Code / OpenCode 接入、model-aware adapter、tool-loop protocol

DeepSeek 在 8 月 13 日正式推出新版 **V4-Pro-0813**。独立报道显示，新版 Pro 相比 V4 Flash 在综合智能、工具使用、编码和 Agent 工作负载上有明显提升；DeepSeek 官方文档也已经把 V4-Pro 作为 Coding Agent 的主力模型接入 Claude Code、OpenCode 和 OpenClaw。

更值得开发者关注的不是单个 Benchmark，而是 DeepSeek 官方给出的 **角色化模型路由**。在 Claude Code 的推荐配置中：

```text
主 Agent / Opus / Sonnet → deepseek-v4-pro[1m]
子 Agent / Haiku       → deepseek-v4-flash
```

也就是说，厂商自己已经默认：**复杂规划交给高能力模型，子任务交给便宜快速模型**。这比“整个 Agent 全程只用一个模型”更像未来真实生产架构。

同时，社区的 `deepseek-harness` 项目专门记录 DeepSeek V4 的协议细节，例如多轮工具调用时 `reasoning_content` 需要原样回传、并行 tool call 的 streaming chunk 可能交错、prefix cache 对前缀变化很敏感等。这个项目不是 DeepSeek 官方组件，但它揭示了一个重要工程事实：

> **API 语法兼容，不等于 Agent 行为兼容。**

很多模型都声称支持 OpenAI / Anthropic 风格接口，但一旦进入长程工具循环，真正决定稳定性的往往是 history serialization、thinking state、tool-call aggregation、cache 规则和 context ceiling。

### 为什么重要

Agent 框架过去常把模型层抽象成：

```text
messages + tools → response
```

但现在更接近：

```text
Model Adapter
├─ reasoning state policy
├─ tool-call merge policy
├─ context ceiling
├─ prefix-cache semantics
├─ retry / error semantics
└─ role-based model routing
```

如果这些协议差异没有被 Harness 正确处理，模型本身再强，也可能在第二轮工具调用就出错。

### 对开发者的实际启发

不要把模型供应商差异散落在业务代码里。建议为每个模型家族维护独立 adapter，并给它配一组小型协议探针：

```text
probe_tool_loop
probe_parallel_tool_calls
probe_reasoning_roundtrip
probe_context_limit
probe_prefix_cache
probe_retry_semantics
```

此外，Coding Agent 可以直接尝试 **Planner/Executor 分层路由**：主 Agent 使用 Pro，搜索、文件读取、简单修改或子 Agent 使用 Flash。这样通常比让最贵模型承担所有工作更容易控制成本。

## 2. GLM-5.3：开放权重模型开始采用“分阶段开放 + 高风险能力门控”

- **标签**：`LLM` `Safety` `Agent` `Cybersecurity`
- **相关技术**：GLM-5.3、trusted access、capability gating、tool-level safety

Z.ai 在 8 月 14 日公布了 GLM-5.3 的部分能力和开放计划。其公布结果显示，GLM-5.3 在漏洞识别任务上已经接近甚至略高于 Anthropic 的受限网络安全模型 Mythos 5，但在把漏洞进一步转化为可执行攻击方面仍明显较弱。

更值得注意的是发布策略：Z.ai 表示会在完成额外安全评估后再公开模型，并计划将最敏感的网络安全能力放进 **trusted access** 机制，只对经过验证的用户开放。

这不是简单的“模型更强了”，而是一个值得关注的行业变化：

> **开放权重 ≠ 所有能力、所有工具、所有运行权限同时无条件开放。**

厂商开始尝试把“权重开放”“高风险能力访问”“外部工具权限”拆成不同层级。

### 为什么重要

对于 Agent 系统，风险往往并不来自模型单次输出，而来自：

```text
模型能力
  ×
工具权限
  ×
凭证范围
  ×
自主运行时长
```

一个能识别漏洞的模型，在只读代码环境里可能是安全助手；同一个模型如果同时拥有公网访问、shell、凭证和自动执行权限，风险就完全不同。

### 对开发者的实际启发

安全控制应该放在 **Tool / Runtime 层**，而不是只靠系统 Prompt：

```text
Agent
 ↓
Policy Gate
 ↓
Scoped Credential
 ↓
Sandbox / Tool
 ↓
Execution Log
 ↓
High-risk Action → Human Approval
```

尤其是自动代码修改、DevOps、数据库和安全分析 Agent，应该把权限细分成 read / write / execute / network / secret-access，而不是给 Agent 一个全能 shell。

## 3. Muse Glimmer：本地小模型开始成为 Agent 的“低成本执行层”

- **标签**：`LLM` `Agent` `Local AI` `Efficiency`
- **相关技术**：Muse Glimmer、distillation、local agent、small worker model

Meta 近期发布了 **Muse Glimmer**，定位不是继续追求最大参数规模，而是让 Agent 型任务可以在普通 Mac / PC、单张消费级 GPU 上本地运行。公开报道显示，Glimmer 是从更强的 Muse Spark 系列蒸馏而来，重点面向 reasoning、coding 和常见 Agent 工作流。

这件事的重要性在于：Agent 系统开始形成越来越清晰的 **模型分层**。

过去常见架构：

```text
所有任务 → 一个 Frontier Model
```

更合理的下一代架构可能是：

```text
Frontier Planner
      ↓
Task Router
 ┌────┼────────┐
Local Worker  Cheap API Worker  Frontier Specialist
```

不是所有步骤都需要最强模型。文件分类、格式转换、日志摘要、简单代码改动、检索结果整理、局部 UI 操作等任务，如果能由本地模型稳定处理，就可以显著减少 API 成本和网络延迟，同时提升隐私性。

### 为什么重要

对长期 Agent 来说，成本并不是“每次调用多少钱”，而是：

```text
单次成本 × 调用次数 × Agent 数量 × 运行时间
```

一个每小时运行几百次工具循环的 Agent，哪怕单次差价很小，长期都会被放大。因此，小模型 Worker 很可能是未来 Agent 经济性的核心组件。

### 对开发者的实际启发

可以把任务先分三类：

```text
A. 高不确定性规划 / 复杂推理 → Frontier Model
B. 可验证执行 / 局部任务       → Local / Small Model
C. 纯确定性处理               → 普通代码
```

尤其不要让 LLM 做本来可以由普通程序完成的 JSON 转换、文件重命名、规则过滤和确定性校验。

如果引入本地 Worker，务必做自己的任务级 Eval；“能本地跑”不等于“适合你的生产任务”。

## 4. Harness Evolution 新论文：自动改 Harness 有价值，但“涨分”很容易是假的

- **标签**：`Agent` `Harness` `Evaluation` `Self-Improvement`
- **相关论文**：HSI、Harness-IF、Rethinking the Evaluation of Harness Evolution、HarnessOpt-Bench

本周的 Harness Evolution 论文开始出现一个很有价值的分化：**一部分工作证明 Harness 可以持续进化，另一部分工作则指出很多所谓“进化收益”其实来自额外搜索预算或 Benchmark 过拟合。**

### HSI：任务专属 Harness 可以在冻结模型上持续改进

*Hierarchical Self-Improvement* 把系统拆成三层：

```text
Task Harness
    ↑ 被修改
Evolver
    ↑ 被修改
Meta-Evolver
```

模型权重保持冻结，真正变化的是外部 Harness。论文在 BALROG 上用 DeepSeek-V4-Flash-Preview 作为固定 backbone，在 BabyAI、Crafter、TextWorld、MiniHack 等中等难度任务上报告明显提升。

但作者自己也给出了两个边界：

- **feedback-fidelity bound**：反馈不够准确，进化就没有方向；
- **backbone capability bound**：如果任务本身超出底座模型能力，Harness 也救不了。

这比“Agent 可以无限自我改进”的叙事现实得多。

### Rethinking Harness Evolution：预算一匹配，很多优势会消失

另一篇论文专门重新审视 Harness Evolution 的评测方法。核心批评是：自动 Harness Evolution 本身会反复跑任务、读反馈、修改配置，这已经消耗了大量 test-time compute。

所以正确对比不应该是：

```text
进化 Harness（跑了很多轮）
vs
固定 Harness（只跑一次）
```

而应该是：

```text
Harness Evolution
vs
同等推理预算的 parallel sampling / sequential refinement
```

论文报告，在 Terminal-Bench 2.1 上做预算匹配后，Harness Evolution 并不能稳定超过简单的 test-time scaling，而且在 held-out task 上迁移收益很弱。

这说明很多“Harness 自动进化 +10 分”的结果，可能只是**花了更多推理预算并对公开 Benchmark 做了搜索**。

### Harness-IF：规则写在哪里，也会改变 Agent 是否遵守

最新的 Harness-IF 更进一步：它不只看最终任务成功，而是单独测试 Coding Agent 在不同 instruction surface 上是否遵守规则，包括 system prompt、project files、user instructions、tool descriptions、skill descriptions。

论文发现，模型对“违背默认习惯”的规则遵守率明显更低，而且不同 instruction surface 的优先级并不简单遵循“越深层越高优先级”。

这对真实 Coding Agent 非常重要，因为生产规则通常同时散落在：

```text
System Prompt
AGENTS.md / CLAUDE.md
User Prompt
Tool Description
SKILL.md
```

如果这些规则互相冲突，模型行为可能远比开发者想象得不稳定。

### 为什么重要

Harness 已经不再是 Prompt Engineering 的别名，而是一个真正需要：

- versioning
- regression test
- held-out evaluation
- compute accounting
- instruction conflict testing

的软件组件。

### 对开发者的实际启发

如果以后让 Agent 自动修改自己的 Prompt、Skill、Tool Schema 或 Context Policy，建议至少设置四道 Gate：

```text
1. Training Tasks：发现候选修改
2. Cost-Matched Baseline：确认不是单纯多花了推理预算
3. Held-out Tasks：确认没有 Benchmark 过拟合
4. Cross-Model / Cross-Repo Test：确认修改有迁移性
```

同时对规则配置做一个简单原则：**同一条关键规则只保留一个权威来源，其余位置引用它，不要复制多份略有差异的版本。**

## 今日判断

今天的新一期最重要的信号不是某个单独模型又涨了几分，而是 **Agent 栈正在快速分层**：

```text
Frontier Planner
      ↓
Model-aware Harness / Protocol Adapter
      ↓
Role-based Model Routing
      ↓
Local / Cheap Worker Models
      ↓
Permissioned Tools + Runtime Gates
      ↓
Verifier / Eval
      ↓
Harness Evolution
      ↓
Held-out Generalization Gate
```

这几层开始互相独立演进。

对普通开发者而言，最值得立即实践的三件事是：

1. **不要假设“OpenAI-compatible”就意味着 Agent-compatible**：给不同模型维护协议 adapter 和回归探针。
2. **不要全程只用最强模型**：主 Agent、子 Agent、确定性代码应该分层路由。
3. **不要只看 Harness 改动后的 Benchmark 涨分**：必须做预算匹配和 held-out 测试，否则很容易把搜索成本或过拟合误认为系统进步。
