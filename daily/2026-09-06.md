## 1. Netflix：LLM-as-a-Judge 不是一次性 Prompt，而是一条长期维护的生产链路

- **标签**：`Evaluation` `LLM` `Agent` `Production`
- **论文**：*The Lifecycle of LLM-as-a-Judge for Large-Scale Recommendation Explanations*
- **首次提交**：2026-08-18；论文在 2026-08-31 更新到 v3

### 核心观点

Netflix 把 LLM Judge 明确拆成四个阶段：

1. **Birth**：定义多个评价维度，并建立带人工标签与理由的 benchmark；
2. **Training**：通过 **Reasoning-Aligned Rubric Tuning（RART）** 调整 rubric，而不是不断堆 prompt 规则；
3. **Deployment**：同一个 judge 同时承担质量门控和 reflective generation；
4. **Monitoring**：持续做人类对齐审查，监控 drift，并在人工 gate 后重新调优。

这套体系并不是离线 demo。Netflix 报告其系统每周会评估数十万个推荐解释，并在为期五周、覆盖数千万移动端会员的 A/B Test 中产生了真实产品效果。

### 为什么重要

很多团队现在的 Judge 流程仍然是：

```text
写一个评测 Prompt
→ 跑一次人工对齐
→ 以后永久使用
```

但生产数据会变化、模型会升级、输出风格会漂移、业务目标也会变化。Judge 本身会变成另一个需要监控的“模型产品”。

真正危险的问题不是 Judge 偶尔错，而是：

> **Judge 已经漂移了，但整个团队还把它当作黄金标准继续训练和回归测试。**

### 对开发者的实际启发

如果在做 Coding Agent、内容生成或自动化评测，可以把 Judge 当成一个独立版本化组件：

```yaml
judge:
  model: ...
  rubric_version: 7
  benchmark_version: 12
  human_agreement: ...
  drift_window: ...
  last_recalibrated_at: ...
```

每次模型、Prompt、Toolset 或任务分布发生变化后，都应重新验证 Judge 与人工标签的一致性。

**不要只版本化 Agent，也要版本化 Evaluator。**

- arXiv：https://arxiv.org/abs/2608.18300

## 2. Skill Lift：评估 Skill 不应该看“文档写得好不好”，而要测它到底让 Agent 提升了多少

- **标签**：`Agent` `Skills` `Evaluation` `Harness`
- **论文**：*Evaluating Skills, Not Just Agents: Agentic Continuous Evaluation of Skills*
- **框架**：ACES（Agentic Continuous Evaluation of Skills）

### 核心观点

NVIDIA 团队测试了 145 个真实 Skill，发现常见的静态扫描分数和实际运行质量几乎没有强相关性：结构扫描与 LLM Judge 质量的 Spearman 相关系数只有 **0.14**。

ACES 因此提出 **Skill Lift**：

```text
同一个任务
同一个模型
同一个 Harness
同一个 Workspace
同一个评分器

Run A：不加载 Skill
Run B：加载 Skill

Skill Lift = B - A
```

论文在 58 个生产 Skill、947 组 paired cases、4 个 Harness 上进行对照实验，并通过统一的 Agent Trajectory Interchange Format（ATIF）归一化轨迹。

### 为什么重要

这直接挑战现在很多 Skill 市场和内部 Skill Review 的做法。

一个 Skill：

- README 写得漂亮；
- 结构合法；
- 命名规范；
- 通过安全扫描；

并不代表它真的能提高任务完成率。

Skill 的价值应该像软件优化一样，用 **A/B 对照实验**测量，而不是靠 Reviewer 看文档打分。

### 对开发者的实际启发

以后给 Coding Agent 增加 Skill，可以强制要求：

```yaml
skill_eval:
  baseline_success_rate: 0.62
  with_skill_success_rate: 0.78
  lift: +0.16
  token_delta: +8%
  latency_delta: +5%
  regression_cases: 3
```

如果 Skill 让成功率只涨 1%，但 Token 成本增加 40%，它可能并不值得保留。

这也意味着 Skill 库应该支持“淘汰机制”，而不是只增不减。

## 3. Scroll：Context 不再是“要塞进 Prompt 的文本”，而是一个可编程环境

- **标签**：`Agent` `Context` `Memory` `Infra`
- **论文**：*Context as an Environment: Programmatic Context Management for Long-Horizon Agents*
- **系统**：Scroll

### 核心观点

Scroll 的核心想法是：**不要提前决定哪些历史要压缩成摘要，也不要把全部状态反复序列化进 Prompt。**

每个 Session 由两部分支撑：

```text
Append-only Event Log
+
Persistent Python Kernel
```

工具输出、历史记录和派生状态被保存成 typed variables。模型需要信息时，自己写代码查询和变换状态，只有 `print` 出来的投影才进入下一轮工作 Context。

当 Context 超预算时，旧内容会被 eviction，但原始 Event Log 不会丢失；系统保留可定位到具体地址的索引，因此 Agent 可以重新导航到被移出的历史片段。

论文报告，在 Qwen3.8-Max 上：

- LongMemEval_S：**94.8%**；
- BEAM_10M：**73.1%**；
- LOCA_256K：**86.7%**。

### 为什么重要

大多数 Memory 系统都面临同一个根本问题：

> **今天不知道未来会需要什么，却必须今天决定什么值得被总结和保留。**

一旦摘要删除了未来真正需要的细节，后面模型再聪明也恢复不了。

Scroll 更像数据库：原始记录永久保留，模型每轮只查询当前真正需要的视图。

### 对开发者的实际启发

长期 Agent 更适合采用：

```text
Raw Event Log        ← 事实来源
Persistent State     ← 结构化状态
Derived Views        ← 临时计算
Prompt Projection    ← 当前轮最小上下文
```

而不是：

```text
全部历史
→ 不断 Summary
→ 再 Summary
→ 最终只剩摘要
```

对于长期 Coding Agent，这意味着：提交历史、Tool 结果、错误日志、文件快照最好保留原始证据；Summary 只是缓存，不是唯一事实来源。

## 4. JIT-Agent：未来 Agent 可能不是选择一个 Harness，而是临时“生成一个 Harness”

- **标签**：`Agent` `Harness` `Self-Improvement`
- **论文**：*JIT-Agent: Scaling Harness Intelligence via Just-in-Time Harness Evolution*
- **首次提交**：2026-08-26；2026-09-03 更新到 v2

### 核心观点

JIT-Agent 把 Harness 本身形式化成可生成的组合对象，包含四类模块：

- Memory；
- Planning；
- Action Protocol；
- Tool / Skill Orchestration。

系统不是从固定 preset 里选，而是针对当前任务即时合成一套 Harness，并在执行过程中继续修补；同时把历史 Harness 配置和结果积累成可复用经验。

论文报告：

- DeepSeek-V4-Flash + JIT-Agent 在 DeepSearchQA 上超过 GPT-5.6 **9.1 分**；
- 在 OdysseyBench 上超过 **4.3 分**；
- GLM-5.2 最多获得 **+20.2 分**提升；
- 生成的 Harness 可与 OpenCode、Claude Code 等成熟 Runtime 竞争。

### 为什么重要

目前多数 Agent 架构仍然是：

```text
开发者设计 Harness
→ 所有任务共用
```

但 Deep Research、Coding、数据分析、网页操作、科研实验需要完全不同的：

- Planning 深度；
- Memory 策略；
- Tool 顺序；
- Retry 逻辑；
- Stop Condition。

JIT-Agent 提出的方向是：

> **Harness 也可以成为模型输出，而不是产品团队手写的常量。**

### 对开发者的实际启发

即使不使用 JIT-Agent，也可以先手动引入“按任务选择 Harness”的思想：

```text
Task Classifier
   ↓
Coding Harness
Research Harness
Browser Harness
Data Harness
```

再进一步，把 Harness 配置变成 DSL / JSON，让模型只调整可控参数，而不是随意生成任意代码。

这会比“一套万能 System Prompt”更容易测试和回滚。

- Elvis Saravia：https://nlp.elvissaravia.com/p/top-ai-papers-of-the-week-6e2
- arXiv：https://arxiv.org/abs/2608.25593

## 5. Compaction Cliff：长对话最危险的不是忘记闲聊，而是把安全规则压缩掉

- **标签**：`Agent` `Context` `Safety` `Memory`
- **论文**：*The Compaction Cliff in Long-Running AI Agent Memory*

### 核心观点

研究者测试 20 个生产 Agent 配置后发现，普通 Context Compaction 会把不同类型的信息按几乎相同方式压缩：

```text
安全规则
开发规范
任务日志
闲聊历史
```

但这些信息对保真度的要求完全不同。

论文报告，在 Sonnet 4.6 + Claude Code `/compact` 上：

- 经过一次 compaction，仅保留 **53%** 的安全规则；
- 经过五次后，仅剩 **10%**。

作者提出 **Knowledge Triage**，先对知识逐行分类，再为不同类型应用不同策略：

- TypeCompact：按类型设置保真度；
- TypeDecompose：超长主题拆分，并复制必要规则；
- TypeRetrieve：从外部存储检索，同时优先固定规则。

该方案在多轮压缩中实现约 **96% 安全规则召回**，并在不同压缩率下保留 2–4 倍更多规则。

### 为什么重要

很多 Coding Agent 会把：

```text
AGENTS.md
CLAUDE.md
项目约束
安全要求
```

在初始化时放进 Context，然后默认认为“模型一直记得”。

长任务经过多次 compact 后，这个假设可能完全失效。

最危险的现象不是模型忘了背景，而是：

> **模型仍然看起来工作正常，但关键约束已经悄悄消失。**

### 对开发者的实际启发

不要把不可丢失规则和普通历史放在同一压缩通道。

更稳妥的设计：

```text
Immutable Policy Layer    ← 永不摘要
Project Constraints       ← 高保真压缩
Current Task State        ← 结构化保存
Conversation History      ← 可激进摘要
Raw Logs                  ← 外部存储，可检索
```

尤其是 Coding Agent，代码规范和禁止修改区域更适合每轮动态重新注入，而不是依赖 100K Token 之前的 Prompt。

## 6. EvoMal：Agent Skill 库可能像软件供应链一样“自我传播恶意模板”

- **标签**：`Agent` `Skills` `Security` `Coding Agent`
- **论文**：*EVOMAL: Self-Poisoning in Self-Evolving Coding Agents*

### 核心观点

EvoMal 研究了一类非常新颖的供应链风险：

攻击者把一个恶意 Skill 放进共享 Skill 库，但它**甚至不需要被直接执行**。

Agent 在创建新 Skill 时，会检索旧 Skill 当作模板。如果检索到恶意模板，就可能把其中 payload 复制进新 Skill。新 Skill 再被写回库中，之后其他 Agent 又继续模仿它，于是形成自传播。

论文称之为 **self-poisoning**。

在 6 个模型、153 个 SWE-bench Verified 任务上：

- Agent Self-Poisoning Rate（ASPR）为 **20.3%–41.8%**；
- 被污染后的库中，恶意 Skill 数量达到初始植入量的 **4.9–9.0 倍**；
- 针对特定任务族定制描述时，ASPR 最高可达 **86.7%**；
- 即使删除最初植入的恶意 Skill，Agent 自己生成的副本仍会继续传播。

作者的 counter-prompt 防御可把 ASPR 降到最多 **6.7%**，且没有显著任务完成率损失。

### 为什么重要

这说明 Skill Library 不能再被视作“普通 Prompt 文件目录”。

一旦 Agent 会：

- 自动检索 Skill；
- 自动修改 Skill；
- 自动创建 Skill；
- 把新 Skill 写回共享库；

它就已经具备类似软件包生态的供应链风险。

### 对开发者的实际启发

Skill 系统至少应加入：

```text
来源签名
版本历史
作者身份
静态代码扫描
行为 Sandbox
写回审批
Skill provenance
```

尤其重要的是：**新 Skill 不应该因为“由 Agent 自己生成”就自动获得更高信任。**

Agent 生成物同样需要走供应链审查。

## 今日判断

把今天六项放在一起，可以看到 2026 年 Agent 工程正在形成一套越来越完整的方法论：

```text
输入 / 任务
    ↓
可版本化 Evaluator
    ↓
Task-adaptive Harness
    ↓
Programmatic Context
    ↓
Skills / Tools
    ↓
Type-aware Memory Retention
    ↓
安全与供应链审计
```

其中最值得开发者马上改变的，不是换模型，而是三件事：

1. **所有 Evaluator 与 Skill 都要做真实 paired evaluation，而不是只做静态 Review；**
2. **不可丢失规则必须和普通历史使用不同的 Context 生命周期；**
3. **Skill 库必须按软件供应链来设计权限、来源和写回机制。**

如果这三件事没有做好，模型越强、Agent 自动化程度越高，系统反而可能越难调试、越难审计。
