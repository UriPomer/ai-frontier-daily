## 1. Zed Delta：Agent Coding 的下一层不是更大的 Chat，而是“代码 + 对话 + 意图”一起同步

- **标签**：`Coding Agent` `Collaboration` `IDE` `Agent UX` `Context`
- **产品**：Delta
- **发布**：2026-08-12，private beta

### 核心观点

Zed 发布的 **Delta** 不是简单地给 IDE 加一个 Agent 面板，而是把整个协作模型改成：

```text
Conversation Thread
      ↕
Live Worktree
      ↕
Humans + Agents
```

其底层 **DeltaDB** 会把对话和 worktree 一起实时复制。Zed 官方强调：每次编辑与每段讨论都被捕获在 commit 之间；开发者仍然可以正常 commit / push，未使用 Delta 的成员看到的仍是普通 Git 仓库。

更值得注意的是 Review 模型。传统代码评审通常附着在某个 commit / diff 快照上，一旦代码继续变化，评论很容易失去上下文。Delta 则允许评论直接锚定到：

- 当前 worktree 的具体代码行；
- Agent 的计划步骤；
- 对话中的某段文本；
- thinking block / diff；

并随着代码继续演化保持连接。

如果发现实现有问题，不必重新从 diff 猜“Agent 当时为什么这么改”，而可以在同一个 thread 里直接要求它解释或修复。

Delta 还支持：

- 多人实时加入同一 Agent thread；
- 每个参与者拥有同步的本地代码副本；
- 把任务移动到 cloud runner，关闭笔记本后 Agent 继续工作；
- 浏览器直接打开共享 thread；
- 接入第三方 Harness，首个明确支持的是 Claude Code。

### 为什么重要

Git 很擅长保存：

```text
代码变成了什么
```

但 Agent Coding 越来越需要保存：

```text
为什么这么改
谁要求这么改
Agent 当时看到了什么
哪些方案被否掉了
哪条评论触发了下一次修改
```

也就是说，未来代码资产可能不仅包含 **source history**，还需要一个 **intent history**。

这和前几天提到的 Catastrophic Remembering、Harness event log、StateM 的长期状态其实是同一条主线：只保留最终结果，会让后续 Agent 丢失导致结果形成的因果信息。

### 对开发者的实际启发

即使不使用 Delta，也可以开始把 Agent 产生的“意图轨迹”变成一等数据，而不是临时聊天记录。

建议至少保存：

```yaml
task_id: issue-1842
intent: 修复资源热重载导致的崩溃
constraints:
  - 不修改序列化格式
decisions:
  - rejected: 全局重建资源缓存
    reason: 会造成明显卡顿
  - chosen: 只重建失效资源句柄
verification:
  - test_resource_reload
  - editor_playmode_smoke
code_ref: commit / worktree snapshot
```

这样后续人类或 Agent 接手时，不需要仅靠 diff 重建背景。

对于大型 Agent Coding 系统，可以把三种历史明确区分：

```text
Git History        → What changed
Execution Trace    → What happened
Decision / Intent  → Why it changed
```

三者最好能互相引用，而不是全部塞进一个超长聊天记录。

## 2. 138K Agent Skills 研究：Skill 最大的问题不是“不够聪明”，而是根本没有被当作可发布的软件包

- **标签**：`Agent Skills` `SKILL.md` `Context Engineering` `Quality` `Security`
- **论文**：*What Keeps Agent Skills from Being Reusable? Evidence from 138K SKILL.md Files*
- **提交日期**：2026-08-09
- **arXiv**：2608.08453

### 核心观点

这篇论文分析了：

- **138,133 个公开 `SKILL.md`**；
- 来自 **20,556 个仓库**；
- 使用一个两层、7 类、31 项检查的 defect taxonomy。

最醒目的结果是：

- **91.8%** 的 Skill 至少包含一种检测到的缺陷；
- **89.3%** 违反了官方规范中的至少一项要求。

但论文最重要的结论其实不是这个数字，而是**失败类型很普通**：

- routing metadata 写得差；
- body 太长、充满不可执行内容；
- scripts / references / assets 组织不合理；
- 把本地路径、安装记录、changelog、甚至凭证或危险命令一起打包进去；
- 依赖某个特定模型、平台、OS 或原始仓库环境。

也就是说，大量 Skill 的问题更像：

> 一个 README 被复制出来以后，被误认为是一个“可复用模块”。

而不是 Skill 里的自然语言“写得不够漂亮”。

### Skill 的 description 其实是路由接口

论文特别强调 `description` 的作用。

Agent 通常在启动时只加载 Skill 的元数据，然后根据 description 决定要不要加载完整 Skill。因此：

```yaml
name: code-review
description: Review code.
```

这种描述虽然人类能看懂，但作为路由接口非常弱。

更合理的描述应该同时包含：

```text
做什么（capability）
+
什么时候用（trigger）
```

例如：

```yaml
description: Review a code change for correctness, regressions, and maintainability. Use when asked to review a diff, PR, patch, or proposed implementation before merge.
```

论文对 20,000 个 Skills 做了确定性的 routing stress test，发现 routing metadata 合规的 Skill 更容易从启动描述中被正确检索。

### Progressive Disclosure 不是风格，而是运行时成本控制

官方 Agent Skills 规范推荐：

```text
startup:
  metadata only     ≈ ~100 tokens

activated:
  SKILL.md body     < ~500 lines / < ~5K tokens

on demand:
  scripts/
  references/
  assets/
```

这意味着 `SKILL.md` 不应该把所有文档、代码示例和背景知识全部内联进去。

Skill 本质上更像：

```text
小型路由入口
    ↓
明确执行流程
    ↓
需要时再打开资源
```

而不是“给 Agent 看的一篇百科全书”。

### 为什么重要

这篇论文把 Skill 从 Prompt Engineering 重新定义成了一个**软件供应链问题**。

一个 Skill 要真正可复用，必须依次通过：

```text
Can it be discovered?
        ↓
Can it be loaded?
        ↓
Can resources be found?
        ↓
Can it execute safely?
        ↓
Can it survive another repo / model / OS?
```

其中任一步失败，“Skill 写得多专业”都没有意义。

论文还观察到：标记为 AI 生成的 Skill 在安全性和可移植性方面出现更多问题。这不意味着 AI 不能写 Skill，而是说明**直接生成 → 直接发布**缺少传统软件开发里早已习惯的 lint / test / review gate。

### 对开发者的实际启发

最值得直接落地的是给 Skill 建一个 CI。

例如：

```text
SKILL.md
   ↓
Schema / Frontmatter Lint
   ↓
Routing Description Check
   ↓
Body Size / Structure Check
   ↓
Local Path / Credential Scan
   ↓
Dangerous Command Scan
   ↓
Resource Reference Check
   ↓
Small Retrieval / Invocation Test
   ↓
Publish
```

其中可以先用确定性规则解决大部分廉价问题，不要让 LLM 承担所有检查。

建议把 Skill 的生成规范固定成：

1. **名字尽量稳定，不因为翻译正文随意改名**；名字是接口标识，不是营销标题。
2. Description 必须回答 **what + when**，优先保证可路由性。
3. `SKILL.md` 只留执行所需的最小流程；长示例、背景说明外置到 `references/`。
4. 可执行逻辑尽量放 `scripts/`，不要让模型每次重新生成同一段确定性代码。
5. 禁止硬编码用户路径、密钥、账号、平台私有假设。
6. 对危险 shell、`--no-verify`、关闭安全检查等行为设置不可绕过的 gate。
7. 发布前至少跑一次“陌生仓库 / 干净环境”复用测试。

Skill 未来如果真的成为 Agent 生态中的依赖包，那么最需要补齐的可能不是更多 Skill，而是类似：

```text
formatter
linter
package validator
security scanner
compatibility test
registry metadata
```

这会比单纯增加 Prompt 模板更有价值。

## 3. Grok 4.6：模型训练目标正在从“会调用工具”升级成“能在一个 Harness 里持续工作”

- **标签**：`LLM` `Agent` `Long Horizon` `Coding` `Training`
- **模型**：Grok 4.6
- **发布日期**：2026-08-12

### 核心观点

SpaceXAI 对 Grok 4.6 的官方定位非常明确：重点是 **long-running agents** 和更复杂的 interactive / visual work。

比 Benchmark 数字更值得关注的是它披露的训练方式：

1. 先做更长的 supplemental training，并加入工程与高级技术数据；
2. 使用 Grok 4.5 重新生成 SFT trajectories；
3. 这些轨迹横跨不同 reasoning effort、**agent harnesses** 与 STEM / 软件工程 / knowledge work 等领域；
4. 再进行广泛的 agentic RL，包括：
   - knowledge work；
   - general coding；
   - kernel optimization；
   - web development；
   - CAD 等领域环境。

这说明 Agent 模型的训练单位正在从：

```text
单条 prompt → 单条 answer
```

逐渐变成：

```text
Harness
  +
多步 trajectory
  +
工具与环境反馈
  +
长程成功 / 失败结果
```

### 为什么重要

前几天的很多论文都在说明“同一个模型换 Harness，表现可以差很多”。Grok 4.6 的训练信息则从另一面说明：**模型供应商也开始主动把 Harness 多样性放进训练分布。**

这可能会改变“模型能力”和“Harness 能力”的边界。

以前我们会把错误简单分成：

```text
model problem
or
harness problem
```

未来更接近：

```text
Model × Harness compatibility
```

如果模型在训练时已经见过：

- 长工具循环；
- 不同工具协议；
- 多种 Agent scaffold；
- 自测试 / verification；
- 多轮产品迭代；

它进入新 Harness 后的适应性很可能本身就是一种模型能力。

### 官方评测应该怎么读

SpaceXAI 官方报告 Grok 4.6 相比 4.5 在多项 Agent / Coding Benchmark 上提升，并给出了包括 CursorBench、DeepSWE、FrontierCode、APEX-Agents、Terminal-Bench 等成绩。

这些数字是**厂商自报或厂商整理的公开结果**，不应被当成完全独立的第三方比较。

真正值得开发者自己测的是：

```text
任务完成率
cost / successful task
平均工具调用次数
wall-clock time
上下文增长速度
恢复失败率
修改后自验证率
```

官方 API 当前公布的 Grok 4.6 起始价格是：

- **$2 / 1M input tokens**；
- **$6 / 1M output tokens**；
- fast variant 价格为两倍。

对于长程 Agent，单 token 价格不是最关键指标，关键仍然是**每个成功任务最终花多少**。

### 对开发者的实际启发

#### 1. Eval 必须测试“持续工作”，不能只测第一步

一个真正的 Agent Eval 应该故意加入：

```text
多轮工具失败
中途改需求
执行后验证
上下文压缩
恢复运行
分阶段提交
```

否则测出来的只是“第一轮反应能力”。

#### 2. 把 Harness compatibility 做成模型准入测试

引入任何新模型前，至少跑：

```text
protocol round-trip
parallel tool calls
context compaction
retry semantics
long trajectory
resume / checkpoint
verification behavior
```

不要因为 API 格式兼容就默认 Agent 行为兼容。

#### 3. 训练 / 微调自己的小模型时，也应记录 Harness 分布

如果未来做领域 Agent SFT，不要只保存 `(prompt, answer)`。

更有价值的数据结构是：

```text
state_before
available_tools
harness_policy
model_action
observation
verification
state_after
final_outcome
```

这样才能训练模型学会“在系统里工作”，而不只是生成看起来正确的文本。

## 今日判断

今天补充的三项其实形成了一个很清晰的 Agent 工程闭环：

```text
Skill
  → 如何把程序性知识可靠打包

Model
  → 如何在 Harness 中持续执行

Collaboration Runtime
  → 如何让人、Agent、代码和意图长期共存
```

过去很多 Agent 产品把重点放在“模型回答得更聪明”。最近这批进展则越来越像传统软件工程：

- Skill 需要 lint、packaging、compatibility test；
- Model 需要 protocol / harness compatibility eval；
- Agent 工作需要 durable history 与协作状态；
- Review 需要保留代码背后的意图，而不是只看最终 diff。

对开发者最实际的一条建议是：**把 Agent 产生的自然语言资产当作代码资产管理。**

包括：

```text
SKILL.md
AGENTS.md / CLAUDE.md
Agent decisions
Tool policies
Harness configs
Evaluation recipes
```

它们都应该拥有稳定标识、版本、原因、校验器和迁移策略，而不是每次“让 AI 重写一下”。
