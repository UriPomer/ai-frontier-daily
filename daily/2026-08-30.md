## 1. GLM-5.3-Flash：开源大模型开始围绕 Agent 的长期运行成本重新设计架构

- **标签**：`LLM` `Agent` `Multimodal` `Infra`
- **发布时间**：2026-08-26
- **模型**：GLM-5.3-Flash

### 核心观点

Z.ai 发布的 GLM-5.3-Flash 是 GLM-5 系列首个原生多模态模型：

- **320B 总参数，18B 激活参数**；
- 原生支持文本、图像等多模态输入；
- 使用 **Sparse Attention + Linear Attention** 的混合注意力架构；
- 引入 **Manifold-Constrained Hyper-Connections（mHC）**；
- 训练数据规模为约 **30T 多模态 token**；
- 权重采用 **MIT License**；
- 官方模型卡强调其设计目标是降低长上下文与 Agent workload 的服务成本。

模型卡中特别值得注意的是，GLM-5.3-Flash 不只是一个“缩水版旗舰模型”。它重新训练了 base model，并针对长上下文效率重做注意力和连接结构。

### 为什么重要

过去两年大模型最常见的扩展路径是：

```text
参数更多
→ Context 更长
→ 推理更贵
→ Agent 每次 Tool Loop 的成本更高
```

但 Agent 与普通聊天不同。一个任务可能调用模型几十次，且上下文越来越长，因此单次 token 的效率差异会在整个任务中被反复放大。

GLM-5.3-Flash 代表的方向是：

> **Agent 模型不能只优化单轮 benchmark，还必须优化长上下文下的单位有效计算。**

### 对开发者的实际启发

如果在做长期 Coding / Research Agent，评估模型时不要只比较 benchmark，可以记录：

```yaml
cost_per_successful_task:
  input_tokens: ...
  output_tokens: ...
  tool_calls: ...
  wall_time: ...
  total_cost: ...
```

另外，MoE 模型的“18B active”并不代表它只需要 18B 模型的显存：**总参数仍决定权重存储与部署规模**。本地部署时要区分：

- Active Params → 每 token 计算量；
- Total Params → 权重内存、跨卡通信、部署复杂度。

## 2. Qwen3.8-Flash-Next：Qwen4 的重点不是单纯扩大模型，而是重做长上下文计算结构

- **标签**：`LLM` `Architecture` `Agent` `Multimodal`
- **发布时间**：2026-08-26
- **模型**：Qwen3.8-Flash-Next

### 核心观点

Qwen 官方将 Qwen3.8-Flash-Next 明确定义为：

> **未来 Qwen4 架构的 experimental preview。**

其语言模型部分为：

- **125B 参数，6B 激活参数**；
- 额外包含约 **51B N-gram embedding 参数**；
- 48 层；
- 原生 262K Context，可扩展至约 1M；
- 多模态模型，支持图片与视频输入。

真正值得关注的是四个架构变化：

### ① Qwen Sparse Attention（QSA）

Qwen 把此前的 attention path 重构为：

```text
Gated DeltaNet
+
Qwen Sparse Attention
```

QSA 不是逐 token 选择，而是在 **micro-block** 级别选择需要参与注意力计算的区域，目标是显著降低长上下文 latency。

### ② Gated Residual

Residual Stream 不再只是固定相加，而是引入数据相关的 read gate 与 branch-level write gate，让模型可以动态控制不同残差分支的信息流。

### ③ N-gram Embedding

Qwen 把 embedding 作为一种新的“低计算成本扩参维度”。相比 MoE expert，embedding 参数更适合 offload，因此可以用较少计算增加模型容量。

### ④ 新训练配方

Muon 与 AdamW 分别处理不同权重类别，并取消传统 batch-size warmup，直接从目标 batch size 开始训练。

### 为什么重要

这是一个很强的架构信号：下一代模型竞争可能不是：

```text
100B → 300B → 1T
```

而更像：

```text
如何让 1T 参数中
只有很少一部分在每个 token 上真正昂贵地工作？
```

特别是 Agent workload 越来越长，attention 的复杂度和 KV/Context 成本会逐渐压过普通 FFN 计算。

### 对开发者的实际启发

Qwen 官方模型卡有一句很值得 Agent 开发者注意：

> 在多轮 Agent 任务中，降低 reasoning effort 不一定降低整个任务完成时间；单轮更快可能导致分析不足、失败和重试，最后反而增加总 latency 和 token 消耗。

因此 Agent 模型路由更适合优化：

```text
Task Completion Cost
```

而不是：

```text
Single Call Latency
```

## 3. Claude Cowork 内置浏览器：Browser Agent 开始拥有独立的“执行容器”

- **标签**：`Agent` `Browser` `Safety` `Product`
- **发布时间**：2026-08-26

### 核心观点

Anthropic 为 Claude Cowork Desktop 加入了 **Built-in Browser**。

当任务需要访问网页时，Claude 可以在 Cowork 侧边栏里打开自己的浏览器：

- 浏览页面；
- 点击；
- 输入；
- 填写表单；
- 从 Dashboard / Portal 提取数据。

与 Claude in Chrome 最大的区别是：

```text
Claude in Chrome
→ 使用用户已有浏览器会话

Cowork Built-in Browser
→ Agent 自己的浏览器环境
```

Anthropic 明确表示，如果任务不需要访问用户已有标签页、cookie 或浏览器上下文，就可以完全使用独立的 built-in browser。

### 为什么重要

这实际上是 Browser Agent 架构的一次重要分层。

以后浏览器使用可能会被拆成两种权限模型：

```text
低权限：Agent Browser
- 干净环境
- 独立 session
- 默认无个人账号状态

高权限：User Browser
- 登录态
- 邮箱 / CRM / 内部系统
- 更高隐私与操作风险
```

相比“所有网页任务都直接控制用户 Chrome”，这种设计的 blast radius 更小。

Anthropic 同时强调：**Prompt Injection 风险仍然存在**，独立浏览器只能隔离用户个人浏览器状态，并不能解决恶意网页内容诱导 Agent 的问题。

### 对开发者的实际启发

自己的 Browser Agent 也应尽量使用最小权限容器：

```text
Task
 ↓
默认：Fresh Browser Sandbox
 ↓
确实需要登录态？
 ├─ 否 → 继续 sandbox
 └─ 是 → 请求更高权限 session
```

并在真正执行副作用前做独立验证：

```text
网页内容
 ↓
Agent Plan
 ↓
Action Validator
 ↓
click / submit / purchase / send
```

- Anthropic 官方：https://claude.com/blog/cowork-built-in-browser

## 4. Terminal-Bench-Science：科研 Agent 的真实能力仍远低于“能写科研答案”给人的感觉

- **标签**：`Agent` `Evaluation` `Science`
- **Benchmark**：Terminal-Bench-Science 0.1

### 核心观点

Terminal-Bench-Science 将 Terminal Agent 评测扩展到真正的科研工作流。

首个版本包含 **70 个专家设计任务**，覆盖：

- Life Sciences；
- Physical Sciences；
- Earth Sciences；
- Mathematics；
- Engineering。

Agent 不只是回答一个科研问题，而需要实际完成：

- 数据分析；
- 模拟；
- 证明；
- 代码；
- 研究产物。

每个 system 在每个任务上运行 3 次，并通过可复现的 task-specific evaluator 评分。

### 当前结果

官方 0.1 公布的最佳系统：

- **Claude Opus 5 + Claude Code：30.0%**；
- **GPT-5.6 Sol + Codex：22.4%**；
- **Claude Fable 5 + Claude Code：21.4%**；
- 最强开源模型系统 GLM-5.3 约 **8.1%**。

也就是说，即使最强的当前系统也有约 70% 的科研工作流无法完成。

### 为什么重要

这再次证明：

> “LLM 能解释论文”与“Agent 能完成科研流程”是完全不同的能力。

真实科研需要长期维护：

```text
环境
依赖
数据
脚本
中间文件
实验状态
错误恢复
最终可验证产物
```

这也是为什么传统 QA benchmark 越来越难代表 Agent 的实际价值。

### 对开发者的实际启发

如果在做自动实验、数据分析或 AI Scientist，不要只评估最终回答文本。

更好的 evaluator 应检查：

```yaml
artifacts:
  files_exist: true
  code_runs: true
  metrics_reproducible: true
  data_provenance_valid: true
  output_schema_valid: true
```

换句话说：**评估“产物”，而不是只评估“表述”。**

- 官方 Benchmark：https://www.terminal-bench-science.ai/
- 官方结果：https://www.terminal-bench-science.ai/announcement

## 5. OpenAI Jalapeño：Agent 的下一轮成本优势，可能来自推理芯片而不是模型压缩

- **标签**：`Infra` `Inference` `Hardware` `Agent`
- **发布时间**：2026-08-25

### 核心观点

OpenAI 公布了其首款自研 inference chip **Jalapeño** 的第一批实测结果。

官方使用 InferenceX 以及 GPT-OSS 120B、DeepSeek R1、Kimi K2.5 等公开模型进行比较，并报告：

- 峰值吞吐场景约 **1.5–1.9× 更多 AI work / watt**；
- 端到端 latency 约 **1.7–3.6× 更低**；
- 高交互 workload 中性能约 **2.1–4.1× 更高**。

OpenAI 特别强调，这些收益不是只针对自家模型，因此 Jalapeño 更像一个通用 inference architecture，而不是模型专用 ASIC Demo。

### 为什么重要

Agent 对 latency 特别敏感，因为 Agent workflow 是**串行累积延迟**：

```text
模型思考 2 秒
→ Tool 1
→ 模型思考 2 秒
→ Tool 2
→ 模型思考 2 秒
...
```

单轮少 1 秒，如果一个任务有 30 次模型调用，就可能减少几十秒。

因此对于 Agent，硬件的低 latency 往往比纯 throughput 更重要。

### 对开发者的实际启发

以后选择 inference provider 时，应该把下面两个指标分开：

```text
Tokens / Dollar
```

和：

```text
Completed Agent Tasks / Minute
```

后者同时受到：

- TTFT；
- token generation speed；
- KV-cache；
- batching；
- tool wait；
- network latency；
- retry 次数。

对于强交互 Agent，“便宜但慢”的 endpoint 可能反而产生更高的总体工程成本。

- OpenAI 官方：https://openai.com/index/jalapeno-first-results/

## 6. Skild S1：机器人开始真正获得类似 LLM 的 In-Context Learning

- **标签**：`Robotics` `Multimodal` `In-Context Learning`
- **模型**：Skild S1

### 核心观点

Skild AI 发布的 S1 把机器人任务的 Prompt 从语言改成了**视频示范**。

用户给机器人看一段人类第一视角操作视频，S1 在**不微调、不更新权重**的情况下直接执行同一个任务。

Skild 展示的 unseen long-horizon tasks 包括：

- 种植物；
- 做 Pancake；
- 手冲咖啡；
- 组装套件。

这些任务：

- 在 pre-training 中没有出现；
- 最长约 **10 分钟**；
- 包含几十个操作步骤；
- 只使用一次视频示范。

官方报告中，unseen task 的 video-conditioned ICL 相比 language prompting 有约 **7×** 的成功率提升；单次 demonstration 的效果可接近约 380 个 post-training episode。

### 为什么重要

传统机器人开发流程通常是：

```text
新任务
 ↓
遥操作采数据
 ↓
整理数据
 ↓
Fine-tune
 ↓
部署
```

S1 想把它变成：

```text
新任务
 ↓
给机器人看一遍
 ↓
直接执行
```

这几乎就是语言模型从“每个任务都 Fine-tune”走向 Prompt / ICL 的同一条历史路径。

### 对开发者的实际启发

如果这种范式继续扩展，机器人系统的产品接口可能发生变化：

过去：

```text
Robot API = 动作 / Skill
```

未来：

```text
Robot API = Demonstration Context
```

对仿真、游戏和机器人开发者来说，这意味着以后“教 NPC / Robot 新行为”可能不再先写行为树，而是先提供一段示范轨迹，再由通用 policy 做动作对齐与组合。

目前需要注意：S1 的结果主要来自 Skild 自己公布的实验和 Demo，仍需要独立复现与更广泛环境测试。

- Skild AI 官方：https://www.skild.ai/blogs/s1

## 7. AI4AI-Bench：所谓“递归自我改进”，现在真正困难的是让 Agent 敢于修改训练算法

- **标签**：`Agent` `Research` `Self-Improvement` `Benchmark`
- **论文**：*AI4AI-Bench: Benchmarking LLM Agents in Algorithmic Design for Recursive Self-Improvement*
- **提交日期**：2026-08-20

### 核心观点

AI4AI-Bench 专门测试：

> **LLM Agent 能否真正设计更好的 AI 训练算法？**

Benchmark 包含：

- 10 个冻结的 research repository；
- 覆盖 10 类训练算法；
- Agent 有 4 小时在一张 B300 上修改训练算法；
- 修改后的代码从头训练最多 12 小时；
- 使用 Agent 看不到的固定 evaluator 评分。

评分被统一映射为：

```text
0.0 = 无信息模型
0.1 = 仓库原始训练算法
1.0 = 任务最优值
```

### 当前结果

论文测试了 6 个系统、29 种 configuration：

- 平均得分约 **0.166**；
- 最好系统约 **0.250**。

也就是说，当前最强 Agent 也只缩小了“原始算法 → 理论最优”差距的一小部分。

更值得关注的是行为分析：

> **大多数提交根本没有修改模型“如何学习”，只是改了数据、参数或外围配置。**

真正修改 learning algorithm 的少数方案平均表现明显更好。

增加 reasoning budget 的主要作用之一，不只是让修改更聪明，而是让 Agent **更愿意做结构性算法修改**：论文中这一比例从约 8% 提升到 64%。

### 为什么重要

很多“AI 自动科研”Demo 实际上还是：

```text
调学习率
换 batch size
改 prompt
换 dataset
```

而递归自我改进真正要求的是：

```text
修改 optimizer / objective / update rule / training algorithm
```

AI4AI-Bench 第一次把这两类行为比较明确地分开。

### 对开发者的实际启发

如果使用 Agent 自动优化模型训练，不要只允许它改 config。

可以把搜索空间分层：

```text
Level 1: Hyperparameters
Level 2: Data / Sampling
Level 3: Architecture
Level 4: Loss / Objective
Level 5: Optimizer / Training Algorithm
```

然后分别统计 Agent 到底在哪一层产生了改进。

否则“自动科研 Agent 提升 5%”很可能只是自动调参，而不是自动发现了新算法。

- Elvis Saravia：https://nlp.elvissaravia.com/p/ai-agents-weekly-glm-53-flash-hy4
- 论文：https://arxiv.org/abs/2608.20318

## 今日判断：AI Agent 的竞争正在迅速变成一场 Full-Stack Competition

把今天这些进展放在一起，会看到一个非常明显的变化：

```text
                    ┌ Model Architecture
                    │  GLM / Qwen
                    │
用户任务 → Agent ───┼ Browser Runtime
                    │  Claude Cowork
                    │
                    ├ Evaluation
                    │  Terminal-Bench-Science
                    │
                    ├ Inference Hardware
                    │  Jalapeño
                    │
                    ├ Embodied ICL
                    │  Skild S1
                    │
                    └ Self-Improvement Eval
                       AI4AI-Bench
```

以前 AI 产品的差异更多可以解释成：

> “用了哪个模型？”

现在越来越需要问：

> **模型怎么计算？上下文怎么处理？浏览器在哪里运行？工具权限如何隔离？硬件延迟是多少？任务如何验证？Agent 能不能修改自己的训练过程？**

对于普通开发者，我认为今天最值得立刻吸收的三个原则是：

1. **用 Task-level Cost，而不是 API 单价评估 Agent 模型。**
2. **把 Browser / Shell / Tool 执行放进独立、最小权限的 Runtime。**
3. **Benchmark 最终产物和真实工作流，不要只测试聊天答案。**

这三个变化比单纯追逐一次模型排行榜更新更可能持续影响 2026–2027 年的 Agent 工程实践。
