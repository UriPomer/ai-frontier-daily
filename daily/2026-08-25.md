# AI 前沿日报：2026-08-25

## 今日速览

截至 **2026-08-25**，Elvis Saravia 的站点最新一期是 **2026-08-23 发布的《Top AI Papers of the Week (August 17–23)》**。昨天的日报主要覆盖了 8 月 22 日 Agent Weekly 中的 **Self-Improving Agent 脆弱性、dots3-note/TEMPO、DeepSeek Vision 与 Cursor Continuity**，因此今天不重复这些内容，改为从新一期论文周报中筛选 5 个更值得开发者关注的方向：

1. **Agent Lightning v1.0**：把真实部署 Harness 直接接进 RL 训练；

5. **SocialRL**：当 Agent 开始替用户谈判、议价、安排日程，“友好助手”与“利益代理人”其实是两套不同的行为目标。

今天最值得关注的共同趋势是：**Agent 研究正在从“模型更强”转向“Harness 可训练、可持续进化、可测量、可服务，并且能承担真实代理责任”。**

## 1. Agent Lightning v1.0：以后训练 Coding Agent，不必把真实 Harness 重写一遍

- **标签**：`Agent` `RL` `Harness` `Coding Agent`
- **论文**：*Agent Lightning v1.0: Towards Harnessed Agentic RL*
- **提交日期**：2026-08-18

### 核心观点

现代 Agent 的能力并不只来自模型本身。真实部署时通常还有：

```text
Model
 + System Prompt
 + Tool Schemas
 + Context Manager
 + Memory
 + Retry / Stop Logic
 + Sandbox
 + Agent Loop
```

问题在于，传统 Agent RL 往往假设“训练器自己掌控环境交互循环”，但真实 Coding Agent 的 loop 实际由 Harness 控制。于是训练时为了接入 RL，团队经常被迫复制或重写一套执行逻辑，最后训练环境和生产环境发生漂移。

Agent Lightning v1.0 的思路是：**不重写 Harness，而是在 LLM endpoint 边界挂一个 proxy。**

```text
真实 Harness
    ↓
LLM Endpoint Proxy
    ↓
Model / RL Trainer
```

Harness 继续按原来的方式运行工具、上下文和控制流，训练器只观察 LLM request / response 序列，再从这些轨迹中恢复训练所需的数据。

论文把这种模式称为 **Harnessed Agentic RL**。

### 真正困难的地方

论文很有价值的一点是，它没有把问题简化成“代理请求转发过去就能训练”。当 Harness 插在 policy 和 reward 之间时，几个细节会直接破坏梯度质量：

- retokenization；
- 多轮 sample merging；
- advantage calculation；
- loss normalization；
- backend scheduling。

这些问题单看都像工程细节，但如果处理不一致，会让“模型看到的 token 序列”和“训练器计算 loss 的 token 序列”并不完全一致。

### 实验结果

作者报告 Agent Lightning v1.0 本体约 **3,500 行代码**，支持任意 Agent Harness，并给出完整 Coding-Agent RL pipeline。

在仅使用 **6K 训练样本和相对有限计算预算**的情况下，Qwen3.5-9B 在 SWE-bench Verified 上从 **41.8% 提升到 56.4%**，绝对提升 **14.6 个百分点**。

这些结果来自论文作者实验，后续仍需要更多独立复现，但它已经很清楚地证明了：**生产 Harness 本身完全可以直接进入 post-training loop。**

### 为什么重要

这和最近几周的 Harness-R1、LEGO-RL、ClawGym、HarnessCompass 形成了非常一致的方向：

> 真正应该训练的，不只是“一个裸模型”，而是“模型在实际 Harness 中的行为”。

如果 Coding Agent 在生产环境里依赖 repo search、shell、patch tool、context compaction 和特定 stop rule，那么 RL 最好就在这套真实系统里发生，而不是训练完以后再期待模型自动适配另一套执行框架。

### 对开发者的实际启发

如果以后要对自己的 Coding / Research Agent 做 post-training，优先保证：

```text
Production Harness ≈ Training Harness
```

而不是为了训练方便单独做一个简化 environment。

更实用的系统边界是：

```text
Agent Harness
 ├─ Tool execution
 ├─ Context policy
 ├─ Memory
 └─ Control flow
        ↓
    LLM Proxy
        ↓
 ┌───────────────┐
 │ Inference     │
 │ Logging       │
 │ RL Collection │
 └───────────────┘
```

这样以后切模型、做 SFT/RL、跑线上推理时，都能保留同一套 Harness。

- Elvis Saravia：https://nlp.elvissaravia.com/p/top-ai-papers-of-the-week-9b0
- 论文：https://arxiv.org/abs/2608.17528

## 2. Harness Continual Learning：Agent 会遗忘，但遗忘的可能不是模型，而是 Harness

- **标签**：`Agent` `Continual Learning` `Memory` `Harness`
- **论文**：*Harness Continual Learning: Continual Adaptation Beyond Model Parameters*
- **提交日期**：2026-08-19

### 核心观点

传统 Continual Learning 关注的是：模型不断训练以后，会不会发生 catastrophic forgetting。

但现代 Agent 的长期状态很多已经不在权重里，而是在：

- Prompt；
- Memory；
- Skills；
- Tool descriptions；
- Router；
- Capability map。

这意味着即使底层模型完全冻结，修改一个 Harness 组件，也可能把以前稳定工作的能力改坏。

论文把这种现象正式命名为：

> **Harness-Level Forgetting**

### Guarded Harness Evolution

作者提出的关键机制不是“禁止 Agent 自己修改 Harness”，而是把**提出修改**和**真正提交修改**拆开。

```text
任务执行
 ↓
Post-execution feedback
 ↓
Continual Optimizer
 ↓
Candidate Harness
 ↓
Continual Evaluator
 ├─ 当前任务是否变好？
 ├─ 历史能力是否保留？
 └─ Harness 是否仍有效？
 ↓
Commit / Reject
```

这其实非常像软件工程里的：

```text
写代码 → CI → Regression Test → Merge
```

只不过这里被测试的是 Prompt、Memory、Skill、Router 等 Agent state。

### 实验结果

论文在文本推理、多模态感知和 open-world interaction 上做实验，多个设置相对 baseline 的提升超过 **10%**，同时通过 retention sweep 展示了 Harness 更新带来的稳定性—可塑性权衡。

更重要的是，它证明“只看当前任务有没有提升”是不够的：Harness 可能在新任务上更强，却悄悄破坏旧任务。

### 为什么重要

很多所谓“自我进化 Agent”今天实际上都在做：

```text
任务失败
 ↓
LLM 总结经验
 ↓
直接修改 memory / prompt / skill
 ↓
永久保存
```

这本质上就是**没有 CI 的自修改生产系统**。

昨天介绍的 Self-Improving Agent 脆弱性论文已经说明，错误经验会被 task ordering、噪声和环境约束放大；今天这篇进一步给出了工程层面的解决方向：**所有 Harness 更新都需要回归测试。**

### 对开发者的实际启发

如果让 Agent 自动修改自己的 `AGENTS.md`、Skill、Memory 或 Prompt，建议建立类似：

```yaml
candidate_change:
  component: skill
  reason: "..."
  source_runs: [...]
  expected_gain: "..."

validation:
  current_suite: pass
  historical_suite: pass
  schema_check: pass
  regression_delta: -0.3%

commit: true
```

最关键的是维护一个**历史任务保留集**。每次自动改 Harness 后，都跑一遍小型 regression suite；否则“越用越聪明”很容易变成“越用越偏”。

### 来源

- Elvis Saravia：https://nlp.elvissaravia.com/p/top-ai-papers-of-the-week-9b0
- 论文：https://arxiv.org/abs/2608.19013

## 3. Agent Skills：真正有用的是“流程锚点”，而不是塞更多知识

这一期有两篇非常适合放在一起看：

1. *Demystifying Agent Skills: Why They Work—Until They Don't*
2. *@skills: Attention is all you have*

它们分别回答两个问题：

- **为什么 Skill 有用？**
- **为什么 Skill 一多就不好用了？**

### 3.1 Skill 的主要价值：Procedural Anchoring

*Demystifying Agent Skills* 汇总了 **8,135 条标准化 trial record**，并对轨迹做了对照分析。

结果很反直觉：Skill 帮助 Agent 时，主要不是因为“告诉了模型一个它不知道的事实”。

论文统计：

- **65.7%** 的有效案例来自 **procedural anchoring**；
- 只有 **4.5%** 可以归因于显式知识注入。

也就是说，Skill 更像：

```text
不要临场发挥
 ↓
按一个经过验证的流程执行
```

而不是：

```text
给模型补充百科知识
```

论文还发现，Skill 相比 Workflow Memory 在匹配对照中平均高 **6.06 分**。

### 3.2 真正的瓶颈是 Retrieval / Trigger

当 Skill 池从 **5 个增长到 100 个**时，实际使用 precision 从 **29.6% 降到 3.3%**。

这说明 Skill 库增长后，核心问题不再是“有没有这个 Skill”，而是：

> Agent 能不能在正确时刻找到它？

另一篇 *@skills: Attention is all you have* 更直接指出：现在已经有 **56,804 个公开 Agent Skill**，但 system prompt 中真正可靠的自动 trigger slot 少于约 **100 个**。

传统安装模式把三个完全不同的概念绑在一起：

```text
Skill Content
+ Persistence
+ Automatic Trigger
```

但其实只有 Automatic Trigger 必须占用 prompt attention。

因此作者提出把 Skill 分成不同使用层级：

- 只是可查询 Reference；
- 保存的 workflow；
- 真正需要自动触发的 Installed skill。

### 为什么重要

很多团队现在的 Skill 策略是：

```text
发现一个有用 Skill
 ↓
安装
 ↓
继续安装
 ↓
System Prompt 越来越长
 ↓
Skill 选择越来越差
```

这两篇论文合起来给出的结论很明确：

> **Skill 要写成流程，而且 active set 要小。**

### 对开发者的实际启发

比较合理的 Skill 架构可以是：

```text
所有 Skills（几百 / 几千）
        ↓
Search / Retrieval
        ↓
候选 5~10 个
        ↓
当前会话 Active Skills
        ↓
LLM
```

而不是把所有 Skill description 常驻 Prompt。

并且 Skill 文件更适合包含：

```markdown
1. 什么时候使用
2. 输入要求
3. 标准步骤
4. 验证方式
5. Stop condition
6. 常见失败与恢复方式
```

而不是长篇背景知识。

对于 Coding Agent 尤其明显：像“创建 UE Gameplay Ability”“新增 Unity Addressable 资源”“发布 npm package”这类高重复流程非常适合 Skill；而一次性 Bug 的具体修法不值得长期占据自动触发空间。

### 来源

- Elvis Saravia：https://nlp.elvissaravia.com/p/top-ai-papers-of-the-week-9b0
- Demystifying Agent Skills：https://arxiv.org/abs/2608.14036
- @skills：https://arxiv.org/abs/2608.12610

## 4. AgentSysBench：Agent 的主要性能瓶颈，可能根本不在 GPU

- **标签**：`Agent` `Infra` `Serving` `Performance`
- **论文**：*From LLM Inference to Agentic Workloads: Characterization and Implications for Serving Systems*
- **提交日期**：2026-08-15

### 核心观点

今天大多数 LLM serving 系统的假设仍然来自单轮推理：

```text
Request
 ↓
GPU inference
 ↓
Response
```

但 Agent workload 更像：

```text
LLM
 ↓
Search
 ↓
Sandbox
 ↓
LLM
 ↓
Retriever
 ↓
等待外部 API
 ↓
LLM
 ↓
Tool
 ...
```

论文构建 **AgentSysBench**，对 10 个真实 Agent 应用做端到端 instrumentation。

### 几个很值得记住的数字

作者发现：

- 10 个应用中有 **5 个**，非 LLM 组件占据主要 latency；
- 单 session sandbox working set 峰值可达 **28 GB**；
- 同一个 Agent 内，不同任务因为 GPU / CPU / memory-bound 特性不同，latency 最多相差 **32×**；
- 生产 session 会在步骤之间保持状态并空闲 **几分钟到几小时**；
- Search query 和 web fetch 存在大量跨请求重复。

论文把辅助 LLM 调用、Tool Schema、Observation 等非核心计算成本称为：

> **Control-Plane Tax**

### 系统优化结果

四类针对性优化带来明显收益：

- task-aware serving：latency 降低 **29–40%**；
- communication-aware placement：最高 **4.5×** 改善；
- state offloading：内存降低 **4.6×**；
- tool-result caching：消除 **35.2%** 重复 search call，并节省 **19.3%** 总搜索延迟。

### 为什么重要

如果 Agent 很慢，第一反应通常是：

> 换更快 GPU / 更快模型。

但对真实 Agent 来说，瓶颈很可能在：

- Sandbox 启动；
- Repo checkout；
- 文件 I/O；
- Search API；
- Retriever；
- Tool serialization；
- Context 构建；
- 多轮 helper model；
- 长时间 idle state。

所以 Agent Infra 的优化方式更接近分布式系统，而不是单纯做 LLM inference optimization。

### 对开发者的实际启发

自己的 Agent 最好至少打这些 tracing metric：

```text
LLM inference time
Tool latency
Sandbox startup
Retriever latency
Context build time
Serialization time
Idle time
Helper-model tokens
Main-model tokens
Cache hit rate
```

然后按整条 Trace 做 flame graph，而不是只看 TTFT/TPS。

对于本地 Coding Agent，还可以优先尝试：

- shell / search 结果缓存；
- persistent sandbox；
- repo index 常驻；
- 小模型负责 helper call；
- 只在真正需要时把 Tool schema 放进 Context。

- Elvis Saravia：https://nlp.elvissaravia.com/p/top-ai-papers-of-the-week-9b0
- 论文：https://arxiv.org/abs/2608.15127

## 5. SocialRL：当 Agent 代表你谈判时，“友善”可能是一种缺陷

- **标签**：`Agent` `RL` `Multi-Agent` `Social Reasoning`
- **论文**：*From Passive Delegates to Strategic Negotiators: Reinforcing Social Reasoning in Small Language Models with SocialRL*
- **提交日期**：2026-08-13

### 核心问题

当前 Assistant 的训练目标通常强调：

- helpful；
- cooperative；
- polite；
- transparent。

但当 Agent 不只是“回答用户”，而是**代表用户与另一个利益主体谈判**时，这些性格可能产生完全相反的结果。

论文指出，友好的 frontier model 可能会：

- 主动透露用户底价；
- 过早让步；
- 没有建立议价锚点；
- 把“让对方满意”误当成“为委托人争取利益”。

### SocialRL

作者在一个 **4B 模型**上，针对六类 principal-driven 场景训练 SocialRL：

- Deal-or-No-Deal；
- CaSiNo；
- Craigslist；
- Job Interview；
- Calendar；
- Marketplace。

训练后的一个典型行为变化是：

- 买方首次报价低于目标价的比例从未训练时的 **3%** 提升到 **78%**。

作者进一步使用 cascade RL 与 multi-teacher on-policy distillation，把多个领域 specialist 合并成一个统一 4B 模型，报告平均 utility 达到 **0.627**，高于其测试中的 GPT-5.1（0.619）和 GPT-5.2（0.613）。

这些数字来自论文自身实验，不能简单理解成“4B 模型全面强于 GPT-5 系列”；它说明的是：**针对 social strategy 做专门 RL，小模型可以在特定代理任务上获得非常强的效用。**

### 为什么重要

未来 Agent 会越来越多地：

- 自动买东西；
- 订酒店；
- 谈价格；
- 排会议；
- 招聘沟通；
- 处理 Marketplace；
- 与另一个人的 Agent 交互。

这时需要区分两种 Alignment：

```text
Assistant Alignment
目标：让交流友好、有帮助

Delegate Alignment
目标：忠实维护 Principal 的偏好和利益
```

它们并不总是同一件事。

### 对开发者的实际启发

如果 Agent 会代表用户进行有利益冲突的交互，不应该只给它一个笼统 Prompt：

```text
“请友好地帮用户完成任务。”
```

至少要显式建模：

```yaml
principal:
  hard_constraints: [...]
  target: ...
  acceptable_range: ...
  private_information: [...]
  disclosure_policy: ...
  concession_policy: ...
```

并且把“用户利益”单独作为 verifier / reward，而不是只评估对话是否自然。

- 论文：https://arxiv.org/abs/2608.13787

# 今日判断：Agent 栈正在形成四个新的第一类对象

过去一年很多讨论把 Agent 简化成：

```text
LLM + Tools
```

但这一期论文越来越像在告诉我们，真正的生产 Agent 至少需要四个独立的一等公民：

```text
1. Harness
   负责执行、工具、上下文、路由

2. Evolvable State
   Memory / Skills / Prompt / Router

3. Runtime / Serving System
   Sandbox、缓存、状态、异构资源

4. Verifier / Evaluator
   决定是否接受学习、修改与最终行为
```

最值得开发者马上采用的三个实践是：

```text
① 所有 Harness 自修改都先过 regression test

② Skill 不要无限安装；保持小的 active set，其他按需检索

③ Profile 整个 Agent Trace，而不是只 Profile LLM inference
```

如果这三点做对，即使暂时完全不训练自己的模型，也很可能比单纯换一个更大的模型获得更稳定、更便宜的 Agent 系统。
