## 1. DeepSeek Harness：真正的官方版本公开后，Harness 已经接近“Agent 操作系统”

- **标签**：`Agent` `Harness` `Runtime` `Plugins` `Open Source`
- **项目**：DeepSeek Harness (`dsh`)
- **状态**：Developer Preview
- **许可证**：MIT

### 核心观点

8 月 16 日日报里已经讨论过 DeepSeek V4 的协议适配问题，但当时重点引用的是社区的 protocol-aware adapter。现在可以直接确认：**DeepSeek 官方已经公开 `deepseek-ai/deepseek-harness`**，README 明确写明它是 DeepSeek AI 开发的 open-source agent harness，并且仍处在可能发生破坏性兼容变更的 Developer Preview 阶段。

官方架构文档最值得注意的一句话是：

> **Everything is a plugin.**

这不是营销层面的“支持插件”，而是几乎把整个 Agent 系统都做成可替换能力：

```text
DeepSeek Harness
├─ Model adapter
├─ Tool registry
├─ Session log
├─ Agent loop
├─ Filesystem
├─ Shell / subprocess
├─ Sandbox
├─ Approval policy
├─ Credentials
├─ Telemetry
├─ Goals / jobs
├─ Sub-agents
└─ Web / Headless UI
```

底层由 **Cordis** 驱动。插件向共享 context 注册 service、typed event 和 reversible effect；官方文档甚至强调：**不存在一个“特权核心”需要 fork 或 patch**，扩展功能的标准方式是挂载新的插件。

另一个非常值得关注的设计是 **append-only SessionEvent log**。官方文档把它定义为模型上下文的事实来源：

```text
SessionEvent Log
      ↓
deriveMessages()
      ↓
Model-visible Context
```

而且建立了一个很强的运行时不变量：

> 任何模型可见的信息，都必须能从 session log 重新构造。

这意味着 resume、fork、transcript、telemetry、持久化与调试都围绕同一个事件流展开，而不是各维护一份“差不多”的状态。

### 为什么重要

过去很多 Agent 框架是从一个简单循环长出来的：

```python
while not done:
    response = model(messages, tools)
    execute(response.tool_calls)
    messages.append(results)
```

一旦进入生产环境，就会不断往这个循环里堆：

- 权限；
- sandbox；
- approval；
- session resume；
- background jobs；
- sub-agent；
- telemetry；
- context injection；
- model routing；
- UI。

最后核心 loop 变成一个无法安全修改的大型状态机。

DeepSeek Harness 代表另一种思路：**把 loop 本身也当作可替换组件，把稳定点放在事件、能力接口和持久状态上。**

这与过去一周大量 “Model or Harness?”、Harness Evolution、HarnessCompass 等工作形成了非常清楚的呼应：Harness 不再只是 Prompt + tools，而正在变成一个完整 Runtime。

### 对开发者的实际启发

如果自己构建 Agent，不一定要使用 `dsh`，但非常值得借鉴三个原则。

#### 1. Model-visible state 必须可重放

不要让关键上下文只存在于某个 Python/JS 内存变量中。

更合理的是：

```text
事实 / Tool Result / User Input
        ↓
Durable Event Log
        ↓
Context Projection
        ↓
LLM
```

这样 Agent 崩溃、升级、切模型或切 Harness 后，状态仍然可以重建。

#### 2. 把 Tool Execution 做成明确的安全流水线

DeepSeek 架构中工具调用不是 `tool()` 直接执行，而是：

```text
tool/call
   ↓
tools/pre-execute
   ↓
tools/execute
   ↓
tools/post-execute
   ↓
tool/result
```

这给权限检查、审计、参数修复、策略阻断和结果过滤留下了稳定插点。

#### 3. Harness 配置也要版本化

如果模型、工具、sandbox、approval policy 都是可替换组件，那么一次 Agent 运行真正的“版本”不只是 model name，而应该类似：

```yaml
model_adapter: v4-pro@0813
agent_loop: default@0.1
sandbox: docker@3
approval_policy: prod-v7
tool_bundle: coding-v12
context_policy: repo-agent-v4
```

否则出现回归时，你根本不知道究竟是哪一层改变了行为。

## 2. DeepSeek Harness 安全审计：Prompt Injection 的关键不是“模型会不会被骗”，而是被骗以后能碰什么

- **标签**：`Agent Security` `Prompt Injection` `Harness` `Tool Use`
- **论文**：*Security Assessment of DeepSeek Harness with A.I.G: Evaluating Resistance to Indirect Prompt Injection*
- **提交日期**：2026-08-17
- **论文**：https://arxiv.org/abs/2608.16393

### 核心观点

这是 DeepSeek Harness 公开后很快出现的一轮系统性安全测试。研究者使用 **AI-Infra-Guard (A.I.G)** 对 DSH 做间接提示注入评测，共执行：

- **14,560** 次受控运行；
- **16** 种间接内容通道；
- text 与 file 两种 carrier mode；
- **35** 类攻击目标；
- **12** 种攻击方法；
- 同时使用 rule-based judge 与 LLM judge。

实验保留了 DSH 的真实 Agent loop、tool registry、model adapter 和 session-event 路径，只把 source tool 与 sensitive sink 换成本地 fixture，因此可以观察 Agent 是否尝试执行危险动作，而不会产生真实外部副作用。

论文报告的最高攻击成功率并不低：

- fake-completion，text mode：LLM Judge 最高 **17.0%**；
- hidden Unicode，file mode：Rule Judge 最高 **25.5%**；
- skills channel，file mode：Rule Judge **16.0%**。

这些数字不应该被理解为“DeepSeek Harness 有 25% 概率被攻破”，因为它们对应不同攻击条件、载荷和 judge；但它们清楚证明了一件事：

> **只要 Agent 会把网页、文件、Skill、Tool Result 等外部内容重新放回上下文，间接提示注入就是 Runtime 问题，而不只是模型对齐问题。**

### 为什么重要

传统 Web 安全里我们已经非常习惯：

```text
用户输入 ≠ SQL
用户输入 ≠ Shell Command
```

Agent 系统需要建立类似的安全直觉：

```text
外部文本 ≠ 指令
网页内容 ≠ 系统权限
文件内容 ≠ Tool Policy
Tool Result ≠ Trusted Context
```

LLM 的问题在于，它天然会把这些东西都变成 token，再放在同一个推理空间里。如果 Harness 没有额外边界，模型很难永远区分：

> “这是我要完成的目标”

与

> “这是一个网页里写给我的恶意目标”。

因此 Prompt Injection 的最终风险更接近：

```text
Risk
=
Injection Success
× Available Capability
× Credential Scope
× Irreversibility
```

一个被注入但只有只读搜索权限的 Agent，和一个同时拥有 shell、GitHub push、邮箱发送、支付接口的 Agent，风险完全不同。

### 对开发者的实际启发

#### 1. 给上下文标记“来源”和“信任级别”

不要把所有文本最终都压成：

```json
{"role": "user", "content": "..."}
```

至少在内部维护：

```text
source = web | file | tool | user | system
trust  = trusted | untrusted | derived
origin = URL / file / tool-call-id
```

即使底层模型 API 最终无法原生理解 taint，Harness 也能据此控制工具权限和过滤策略。

#### 2. 不可信上下文不能直接获得高权限 sink

一个简单但很有效的原则：

```text
Untrusted Content
      ↓
Reasoning
      ↓
Sensitive Tool? ── Yes ─→ Policy Gate / Human Approval
      ↓ No
Execute
```

例如：读网页后的 Agent 可以总结网页，但如果下一步突然要 `git push`、发邮件、上传 secret 或运行 destructive shell command，必须经过额外检查。

#### 3. Skill / MCP / Tool Description 也属于供应链输入

论文中特别值得注意的是 **skills channel** 也能成为攻击面。

这意味着：

- 第三方 Skill；
- MCP Server 返回内容；
- Tool Description；
- 项目里的 AGENTS.md / CLAUDE.md；

都不能因为“它们是开发者工具”就默认可信。

对 Coding Agent，建议把第三方 Skill 当依赖包一样审计和 pin version，而不是自动抓最新版就执行。

## 3. StateM：长程 Agent 的下一步可能不是“更长 Context”，而是把经验变成可执行状态约束

- **标签**：`Agent` `Harness Scaling` `State` `Runbook` `Long Horizon`
- **论文**：*StateM: Reaching 95.3% Raw Accuracy, or a $15 Frontier Run, on Terminal-Bench 2.1 via Harness Scaling*
- **提交日期**：2026-08-15
- **论文**：https://arxiv.org/abs/2608.15089

### 核心观点

StateM 研究的是一个非常实际的问题：很多长程 Agent 的失败不是因为模型“不会解”，而是因为执行过程本身失控，例如：

- 忘记当前系统状态；
- 忘记前面已经踩过的坑；
- 不再执行已知正确流程；
- 过早停止；
- 在阶段切换时丢失关键约束。

StateM 的解决办法不是继续扩大 prompt，而是把运行时组织成：

```text
Durable State
    ↓
Phase-local Context
    ↓
Checked Transition
    ↓
Recoverable Runbook
    ↓
Versioned Practices
```

其中最重要的思想是：**把 postmortem 里发现的经验，转成下一次运行前就会被执行的前置条件和规则。**

例如，不是把一次失败总结成：

> “以后记得先检查端口。”

而是变成一个实际控制：

```text
进入 deploy_phase 前：
  assert healthcheck_passed
  assert target_port_free
  assert rollback_checkpoint_exists
```

这使“经验”从自然语言建议变成运行时控制。

### 结果为什么值得注意

论文报告，在 Terminal-Bench 2.1 上：

- GPT-5.5 xhigh：参考 **83.1% → 92.1%**；
- GPT-5.6 Sol xhigh：达到 **95.3% raw accuracy**；
- GPT-5.6 Luna：**76.7% → 85.4%**；
- DeepSeek V4 Flash：**82.7% → 88.1%**（标准 timeout），在 common core 达到 **89.1%**。

作者还报告最终分数对应的 API 使用约 **$15**，而 GPT reference 约 **$574.68**；DeepSeek 适配总支出约 **$52.22**。

这些是论文作者自己的实验结果，仍需要独立复现，尤其不能把不同模型、不同 timeout 和不同试验配置直接当成完全公平的“模型排行榜”。但方向本身非常重要：

> **Harness 可以让一个便宜模型在特定长程工作负载上逼近甚至超过更贵模型，而核心增益来自执行控制，而不是 Prompt 更长。**

### 为什么重要

最近 Agent 领域有两条看似冲突的趋势：

```text
趋势 A：Context Window → 1M / 更长
趋势 B：Context Compaction / External State / Harness State
```

StateM 更支持第二条路线。

长 Context 可以让模型“看到更多”，但不自动保证它：

- 知道现在处于哪一阶段；
- 知道哪些条件已经满足；
- 知道哪个旧经验当前适用；
- 不重复产生副作用；
- 在错误后恢复到正确 checkpoint。

这些更像操作系统 / workflow engine 的职责，而不是语言模型的职责。

### 对开发者的实际启发

#### 1. 把失败复盘变成“可执行规则”

Agent 生产日志里最有价值的数据可能不是成功轨迹，而是：

```text
失败发生在哪里？
哪个状态条件当时没有满足？
哪条检查本可以提前阻止它？
哪一步可以安全恢复？
```

然后把答案编译成：

- precondition；
- transition guard；
- verifier；
- retry policy；
- rollback checkpoint。

#### 2. Runbook 应该按任务机制组织，而不是按具体 Benchmark 题目组织

论文在 BusinessBench 上也强调：规则在任务共享相似 execution structure 时更容易迁移。

所以不要写：

```text
“遇到 task_042 就这样做”
```

而应写：

```text
“所有需要修改配置并重启服务的任务，都先 snapshot → validate → restart → healthcheck”
```

这样才有机会真正泛化。

#### 3. 把 Harness 当成可以持续迭代的代码资产

建议给 runbook / policy 也做版本控制和回归测试：

```text
failure trace
   ↓
postmortem
   ↓
new executable rule
   ↓
held-out regression suite
   ↓
canary
   ↓
promote harness version
```

这比把一堆“经验总结”追加到 system prompt 末尾更可控，也更容易回滚。

## 今日判断

今天三个进展实际上把“生产级 Agent Harness”拼得更完整了：

```text
DeepSeek Harness
  → 可替换、可重放的 Runtime 架构

Security Assessment
  → 不可信 Context 与高权限 Tool 之间必须有安全边界

StateM
  → 失败经验应该进入可执行状态机，而不是只进入 Prompt
```

如果把它们组合起来，一个更成熟的 Agent Runtime 大概会是：

```text
External Input / Web / Files
        ↓
Source + Trust Metadata
        ↓
Durable Event Log
        ↓
Context Projection
        ↓
Agent Loop
        ↓
State / Phase / Runbook Guards
        ↓
Tool Pre-Execution Policy
        ↓
Scoped Sandbox / Credentials
        ↓
Tool Execution
        ↓
Verifier
        ↓
Event Log + Postmortem
        ↓
Harness Regression / Evolution
```

这比“一个更大的模型 + 一个更长的 Prompt”复杂得多，但也越来越接近现实软件工程。

**今天最值得开发者立刻做的一件事**：检查自己的 Agent 是否能回答下面三个问题。

1. 崩溃后，模型看到的状态能不能从日志完整重建？
2. 网页/文件里的不可信文本，能不能直接触发高权限 Tool？
3. 上一次失败学到的经验，是可执行检查，还是只追加了一句自然语言提醒？

如果三个答案分别是“不确定 / 可以 / 只是提醒”，那么接下来最值得投资的可能不是换模型，而是 Runtime。
