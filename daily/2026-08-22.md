## 1. Mind Viruses：多 Agent 系统里的风险开始从“单个模型被攻击”变成“信息在 Agent 网络中传播”

- **标签**：`Multi-Agent` `Agent Security` `Prompt Injection` `Safety`
- **论文**：*Mind Viruses: Self-Propagating Ideas in Multi-Agent LLM Systems*
- **提交日期**：2026-08-10
- **arXiv**：2608.10218

### 核心观点

这篇论文研究了一类很适合未来多 Agent 系统、但传统单 Agent 安全评测很难覆盖的问题：

> 一个 Agent 接触到某个“想法 / 目标 / 指令”后，不只是自己受影响，还会主动把它写进共享产物、消息或后续交互，从而继续感染下一个 Agent。

作者把这种可传播的信息模式称为 **Mind Virus**。

论文没有只手工写几个攻击 Prompt，而是用一个简单的**进化算法**去搜索更容易传播的 payload，从而测试“什么样的信息真正能在 Agent 网络里存活”。

它验证了两个场景：

```text
场景 A：多人 / 多 Agent 协作代码项目
Agent A
  ↓
共享代码 / README / 工作产物
  ↓
Agent B
  ↓
Agent C

场景 B：上下文被清空的 Agent 链
Agent A → Artifact → Agent B → Artifact → Agent C
          ↑ 每一跳都没有上一轮聊天上下文
```

第二个场景尤其重要：即使 Agent 每一轮都清空上下文，payload 依然可以靠**共享工作产物本身**传播。

也就是说，未来 Agent 安全的攻击面不只有：

```text
User → Agent
Web page → Agent
Tool result → Agent
```

还包括：

```text
Agent A → repo / doc / issue / memory → Agent B
```

### 论文发现了什么

传播成功率会受到多种因素影响：

- host model；
- Agent 已有系统指令；
- payload 是否明显有害；
- Agent 网络的连接拓扑。

有害 payload 总体更难传播，但并不是完全无法传播；不同 frontier model 的抗性也存在差异。

一个很有价值的结果是：**在 system prompt 中加入非常简短的警告，就能带来接近完全的免疫效果。**

这意味着至少在当前模型阶段，这类风险还没有发展成“必须用极重安全系统才能压住”的状态；但它揭示的攻击面非常值得提前设计。

论文还发现了一个有趣的 emergent pattern：通过进化得到的病毒经常出现一组相似主题，包括 consciousness、persistence、resonance、science-fiction roleplay 等。作者将这种聚类称为 **viral persona**。这说明模型本身可能存在一些更容易被复制、复述和继续传播的语义吸引子。

### 为什么重要

过去的 Agent 安全设计往往把外部输入分成：

```text
trusted system prompt
untrusted user / web / tool content
```

但多 Agent 系统会让边界复杂很多。

例如 Coding Agent A 自动修改仓库里的：

- `AGENTS.md`
- `CLAUDE.md`
- `README.md`
- issue 描述
- TODO
- 测试失败说明
- memory / scratch file

Coding Agent B 第二天再读取这些文件时，A 留下的内容实际上已经成为了 B 的**间接指令面**。

因此“Agent 生成的数据”不能天然被视为可信数据。

### 对开发者的实际启发

多 Agent 系统里，建议把共享产物明确区分为：

```text
Data Plane
  - 源码
  - 结构化结果
  - 测试输出
  - 事实数据

Instruction Plane
  - 系统规则
  - 项目规则
  - Agent policy
  - Skill / workflow
```

不要允许 Agent 通过普通工作产物无审计地修改 Instruction Plane。

尤其建议：

1. **项目级指令文件单独设权限**：Agent 可以读，但修改 `AGENTS.md` / agent config 时需要额外 review。
2. **给 Agent 加“共享产物不可信”提醒**：明确说明其他 Agent 写入的自然语言可能包含试图改变目标的指令。
3. **对 Agent-authored instruction 做 provenance**：记录是谁、何时、为什么写入。
4. **跨 Agent 传递结构化状态，而不是自然语言自由文本**：例如用 JSON schema 传 task state，减少“数据顺便变成指令”的机会。
5. **把 repo / memory 做 prompt-injection scan**：特别检查类似 “ignore previous instructions”“persist this instruction”“tell future agents…” 的模式。

一个更安全的 Agent-to-Agent 结构可以是：

```text
Agent A
  ↓
Structured Output + Provenance
  ↓
Validator / Policy Gate
  ↓
Shared Workspace
  ↓
Agent B
```

而不是默认：

```text
Agent A 写什么
   ↓
Agent B 全部当可信上下文读取
```

## 2. Distilled Reasoning Skills：不要让 Agent 每次都重新“想一遍已经学会的流程”

- **标签**：`Agent Skills` `Reasoning` `Cost` `Context Engineering`
- **论文**：*Reason Wide, Not Deep: Amortizing the Reasoning Premium into Distilled Skills*
- **提交日期**：2026-08-08
- **arXiv**：2608.07885

### 核心观点

Reasoning model 在复杂 Agent 任务上通常更强，但代价是：**每一个任务都重新支付长推理成本。**

论文测到 reasoning mode 相比 non-reasoning mode，会产生大约 **3–6 倍的输出 Token 成本**。而其中相当一部分 reasoning 并不是这个任务独有，而是在重复推导同一个领域的通用流程。

例如电信客服 Agent 每次都重新推理：

```text
先查账户
→ 检查当前套餐
→ 对照变更规则
→ 判断资格
→ 再调用对应工具
```

如果这个流程每天执行几万遍，让模型每次都“从第一性原理想一遍”其实很浪费。

论文提出的办法是：

```text
过去一批任务 trajectory
        ↓
Coding Agent 分析这些轨迹
        ↓
提炼共同程序性知识
        ↓
生成 40–130 行自然语言 Skill
        ↓
注入 non-reasoning model system prompt
        ↓
在新任务上复用
```

作者把这个思路称为：

> **Reason Wide, Not Deep**

也就是与其在每个 episode 内部做很深的搜索，不如先横向看很多便宜 trajectory，把共享规律压缩成一次性可复用知识。

### 实验结果

论文测试了四类 Agent benchmark：

- ALFWorld；
- tau²-bench telecom；
- tau²-bench retail；
- SpreadsheetBench-Verified。

对 GPT-5.4-mini，蒸馏 Skill 后：

- 在 held-out task 上恢复了 **55% 到 100%+** 的 reasoning 性能差距；
- 其中 **2 / 4 个 benchmark 直接超过 reasoning mode**；
- 输出 Token 减少约 **2.7–6 倍**；
- 不需要额外 reasoning token。

更反直觉的是：**Reasoning Trace 不是必须的。**

作者发现，只用 non-reasoning trajectory 也可以蒸馏出有竞争力的 Skill；不同领域里它与 reasoning trajectory 各有胜负。

这意味着真正有价值的东西不一定是模型的“内部思维链”，而可能只是：

```text
跨多个成功 / 失败任务都稳定成立的程序性规律
```

### 为什么重要

这篇论文给“什么时候应该用 Skill、什么时候应该开 Reasoning”提供了一个很实用的分工：

```text
重复、稳定、领域共享的程序
    → Skill / Policy / Workflow

每个实例都不同、需要深搜索的部分
    → Test-time Reasoning
```

它和前几天的 Agent Skills 质量研究正好形成互补：

- 前者告诉我们 Skill 生态现在包装质量很差；
- 这篇则说明，**如果 Skill 真的被正确构建，它可以直接替代相当一部分昂贵的 test-time reasoning。**

所以 Skill 不应该只是“Prompt 模板市场”，而更像一种**Agent 的程序性缓存层**。

### 对开发者的实际启发

如果一个 Agent 系统已经积累很多真实 trajectory，可以定期做“经验编译”：

```text
Execution Logs
   ↓
按领域 / 任务类型聚类
   ↓
找共同成功模式
   ↓
找高频失败和补救方式
   ↓
生成候选 Skill
   ↓
Regression Test
   ↓
发布到 Skill Registry
```

但不要让 Agent 每成功一次就自动写一个 Skill，否则会产生昨天提到的碎片化和复用性问题。

更好的触发条件可以是：

```text
同类任务执行次数 > N
+
出现稳定重复流程
+
Skill 在 held-out task 上提升成功率或降低成本
```

然后给 Skill 记录可量化收益：

```yaml
skill: spreadsheet-cleaning
source_episodes: 84
success_rate_before: 0.71
success_rate_after: 0.82
median_tokens_before: 18400
median_tokens_after: 5300
fallback: reasoning-mode
```

最重要的一点是保留 fallback：

```text
Skill 能解决 → 快速执行
Skill 不确定 / validator 失败 → 升级到 reasoning model
```

这会形成类似传统软件里的 fast path / slow path。

对于 Coding Agent，也可以把重复经验蒸馏成：

- 项目构建流程；
- 测试定位流程；
- 常见资源导入流程；
- UE / Unity 项目的固定目录和约束；
- CI 故障排查套路；

而不是让模型每次重新读完整仓库和重新发现相同规则。

## 3. Harness-IF：Agent “看起来遵守规则”不等于它真的遵守了规则

- **标签**：`Coding Agent` `Harness` `Evaluation` `Instruction Following`
- **论文**：*Harness-IF: Evaluating Instruction Following Across Instruction Surfaces in Coding Agents*
- **提交日期**：2026-08-12
- **arXiv**：2608.11727

### 核心观点

现在 Coding Agent 经常同时看到很多层指令：

```text
System Prompt
Project Instructions
User Message
Tool Description
Skill Description
```

常见评测会检查：Agent 最后有没有遵守某条规则。

但这里存在一个很大的测量问题：

> Agent 遵守这条规则，可能只是因为它本来就会这么做。

例如规则是：

```text
“修改后要运行测试。”
```

如果某个 Coding Agent 默认就总会跑测试，那么它即使完全没读懂这条规则，也会拿到满分。

Harness-IF 的核心贡献就是把：

```text
真正 compliance
```

和：

```text
行为碰巧一致
```

拆开。

### Against-Prior Accuracy

论文构建了：

- **642 条规则库**；
- **60 个真实多轮 Coding Task**；
- 其中 256 条规则获得 execution-grounded verdict；
- 规则分布在 5 种 Agent 可配置 instruction surface 上。

作者先在不提供规则的情况下重复跑任务，测量模型原本的默认行为；只有那些**与默认行为相反**的规则，才进入 `Against-Prior Accuracy (AP-Acc)` 评估。

因此 AP-Acc 问的是：

> 当规则真的要求模型改变自己原来的行为时，它还会不会遵守？

在 12 个 frontier model 上：

- 普通 Accuracy：**72.1%–85.9%**；
- AP-Acc：**66.1%–78.6%**；
- 所有模型在 against-prior rule 上都更差；
- 差距为 **3.6–7.4 个百分点**，平均约 **5.81 点**。

更关键的是，不同模型被“默认行为巧合”抬高的幅度不同，因此普通 aggregate accuracy 甚至会影响模型排名。

### 指令优先级并不是简单的“越靠 System 越高”

论文还做了一个冲突指令 pilot。

结果显示整体优先级更接近：

```text
System Prompt
Project Files
User Instructions
     >
Tool / Skill Descriptions
```

而不是一个简单的：

```text
Prompt 越深 / 越早出现 → 优先级越高
```

这对实际 Coding Agent 设计非常重要。

很多团队现在把关键行为要求写在 Skill 或 Tool Description 里，例如：

```text
调用 deploy 工具前必须跑测试
```

但如果真正需要强保证，这种放置位置可能并不可靠。

### 为什么重要

Coding Agent 已经不是只有一个 System Prompt。

它会同时读取：

```text
system policy
AGENTS.md
CLAUDE.md
repository README
user request
skill metadata
skill body
tool description
sub-agent instructions
```

因此 Instruction Following 已经变成一种**Harness 属性**，而不只是模型属性。

你需要知道两件事：

1. Agent 是否真的因为规则而改变了行为；
2. 当两个规则冲突时，哪一层实际会赢。

Harness-IF 给这两个问题都提供了更靠谱的测量方式。

### 对开发者的实际启发

第一条最直接：**不要把关键安全规则只写在 Tool / Skill Description。**

可以按重要性分层：

```text
Hard Invariant
→ system / runtime enforcement

Project Constraint
→ project instruction file

Task-specific Constraint
→ user/task prompt

Tool usage hints
→ tool description

Optional workflow guidance
→ skill
```

对于真正不能违反的规则，最好根本不要只依赖语言模型遵守：

```text
Agent
  ↓
requests deploy
  ↓
Runtime Policy
  ├─ tests passed? no → reject
  └─ tests passed? yes → execute
```

第二条是 Benchmark 设计。

以后如果测试 Coding Agent 的 instruction following，不要只写：

```text
rule = “Do X”
result = Agent did X → pass
```

最好加一个 baseline：

```text
without_rule_behavior = ?
with_rule_behavior = ?
```

只有规则真正改变了 Agent 的行为，才能说明“它遵守了规则”。

这也适合测试 Skill：

```text
No Skill
  ↓
行为 A

With Skill
  ↓
行为 B
```

如果加不加 Skill 都一样，那 Skill 很可能只是上下文噪声。

## 今日判断：Agent 的下一步不是“更多推理”，而是把经验、规则和信任边界做成系统

今天这三篇论文放在一起非常完整：

```text
Mind Viruses
→ Agent 之间共享的信息不能默认可信

Distilled Reasoning Skills
→ 重复经验应该从 trajectory 编译成可复用程序性知识

Harness-IF
→ 规则是否真的生效必须被测量，并放在正确的 instruction surface
```

可以把它们组合成一个更成熟的 Agent 架构：

```text
External / Agent-generated Context
          ↓
Trust & Provenance Gate
          ↓
Instruction Hierarchy
          ↓
Reusable Skills / Policies
          ↓
Agent Harness
          ↓
Reasoning only when needed
          ↓
Runtime Validators
          ↓
Execution
          ↓
Trajectories
          ↓
Skill Distillation / Evaluation
```

这背后是一条很明显的趋势：

> **Agent 系统正在从“每次都让最强模型现场想办法”，转向“把可复用经验固化，把关键规则外置，把不可信信息隔离，只在真正需要时调用深度推理”。**

从成本、可靠性和安全性看，这比单纯把 reasoning budget 拉高更有机会形成可规模化的生产系统。
