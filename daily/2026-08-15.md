## 核心进展

### 1. Agent Plugins 1.0：Agent 扩展开始出现真正的跨客户端“打包标准”

- **标签**：`Agent` `Infra` `MCP` `Skills`
- **核心技术**：Agent Plugins 1.0 是一个开放、厂商中立的 Agent 扩展打包规范。它没有重新定义 Agent Skills 或 MCP，而是规定一个最小的可移植目录结构：根目录必须有 `plugin.json`，Skill 固定放在 `skills/`，MCP 配置固定放在 `mcp.json`，客户端私有能力通过反向域名命名空间扩展。
- **为什么重要**：此前即使多个 Agent 客户端都支持 Skills/MCP，插件作者仍经常要为不同产品重复封装目录结构、元数据和发现逻辑。Agent Plugins 把“可移植部分”抽成一个共同契约，降低跨 ChatGPT/Codex、Cursor、GitHub Copilot、Kiro、VS Code 等客户端复用同一扩展的成本。
- **开发者启发**：如果你正在做 Agent 工具或 Coding Agent 扩展，应该把“业务能力”和“客户端壳层”分离。可复用逻辑尽量放进标准 Skill/MCP；客户端特定 Hook、命令和 UI 通过独立命名空间扩展，而不是污染公共 manifest。

一个最小包大致是：

```text
my-plugin/
├── plugin.json
├── skills/
│   └── summarize/
│       └── SKILL.md
├── mcp.json
└── com.example.client/
    └── hooks/
```

规范还特别强调了路径边界：插件加载的路径必须留在 plugin root 内，不能通过 symlink 等机制逃逸；组件失败也应尽量局部化，例如一个 MCP server 无法启动，不应让完全独立的 Skill 一起失效。这些细节说明它不是“文件夹约定”而已，而是在向真正的软件供应链格式靠近。

### 2. Qwen3.8-Max：长程 Agent 能力正在和“可扩展真实环境 + 可验证奖励”绑定

- **标签**：`LLM` `Agent` `Coding` `RL`
- **核心技术**：Alibaba 在 8 月 3 日正式发布 Qwen3.8-Max，官方称其总参数规模 2.4T、每 token 激活约 95B，并把重点放在 coding、work、research 与 long-horizon task。相比单纯堆 Benchmark，更值得关注的是其训练和展示方式：扩大真实工作环境、让不同 Harness/Workspace/Task 共同参与训练，并用统一可验证奖励系统覆盖执行结果、文本/视觉 rubric 和 agentic inspection。
- **为什么重要**：这意味着 Frontier Agent 模型的能力提升，不再只是“模型本体更大”。训练数据分布开始显式包含 Harness、工作区复杂度和多天级任务，模型被训练成适应不同运行时，而不是只适应一个固定 Prompt/工具集合。
- **开发者启发**：做垂直 Agent 时，比起只积累问答数据，更值得积累完整的 **环境—动作—反馈—验证结果**。尤其是 Coding Agent，应把 Build、Unit Test、E2E、CI、静态分析和真实应用状态统一成可机器验证反馈，让模型形成闭环，而不是只对最终文本做偏好学习。

Alibaba 官方还披露了一个约 16 天的自主编码案例：Agent 通过 Issue 状态机、dispatcher、monitor/watchdog、CI 和回归测试持续构建一个自演化 harness。这个案例是厂商自测，不能等同于独立 Benchmark，但它很好地展示了生产级长程 Agent 的必要组成：

```text
Requirement
   ↓
Issue / State Machine
   ↓
Agent Execution
   ↓
Build + Unit + E2E + CI
   ↓
Failure Feedback
   ↓
Repair / Re-plan
   ↓
Merge / Resume
```

官方 8 月 3 日公告称模型权重将“下周”开放；截至本次核查，没有在 Qwen 官方公开检索结果中确认到对应权重页面，因此本文不把“已开放权重”写成既成事实。

### 3. Qwen-CUA：Computer Use 的路线正在从 DOM/API Agent 转向“纯视觉 + 原生交互”

- **标签**：`Agent` `Multimodal` `Computer Use` `RL`
- **论文**：*Qwen-CUA: Native Computer Use for (almost) Everything*（arXiv:2608.02352，2026-08-03）
- **核心技术**：Qwen-CUA 使用 397B-A17B 的 MoE backbone，只观察截图，通过键盘和鼠标事件操作软件，不依赖 DOM tree、Accessibility metadata 或任务专用 API。它最多保留 20 张活跃截图，并把更老的视觉历史分块压缩，以同时保持最近证据和稳定 prompt prefix。
- **训练方式**：团队搭建接近 100,000 vCPU 的云端 rollout fleet，支持数万并发环境，构造约 40,000 个可验证任务；训练以完整 trajectory 的可验证奖励为核心，同时使用 trajectory slicing，并在迭代训练中不断刷新监督数据与 RL 任务分布。
- **为什么重要**：GUI Agent 的通用性最终取决于能否像人一样仅凭“看见什么、点哪里、输入什么”工作。DOM/API Agent 虽然更稳定，却很难覆盖桌面软件、远程应用、游戏工具、传统企业软件等环境。Qwen-CUA 表明纯视觉路线开始具备更强的长程能力。
- **结果**：论文报告 Qwen-CUA 在 OSWorld-Verified 上达到 86.2；扩大同一训练配方后的 Qwen-CUA-Max 达到 87.6。论文还报告相较 Qwen3.7，RedTeamCUA 攻击成功率从 36.6 降到 16.4。以上均为论文作者报告结果，仍需独立复现验证。
- **开发者启发**：Computer Use 不应只设计成“截图 → LLM → click”。更稳的架构需要：

```text
Visual State Buffer
      ↓
Recent Screens + Compressed History
      ↓
Planner / Policy
      ↓
Mouse / Keyboard
      ↓
Environment
      ↓
Executable Verifier / Reward
```

对于测试工具、游戏编辑器自动化、桌面 QA 等场景，真正决定可靠性的往往是环境重置、任务 verifier、截图历史策略和失败恢复，而不是单次视觉识别精度。

  - Elvis Saravia, AI Agents Weekly (2026-08-08): https://nlp.elvissaravia.com/p/ai-agents-weekly-agent-plugins-standard

### 4. HarnessCompass：自动进化 Harness 时，最危险的问题是“只在训练任务上变强”

- **标签**：`Agent` `Harness` `Coding` `Evaluation`
- **论文**：*HarnessCompass: Guiding Automatic Harness Evolution toward Generalizable and Effective Agent Harnesses*（arXiv:2608.01918，2026-08-03）
- **核心技术**：HarnessCompass 针对自动 Harness Evolution 的三个典型问题：对演化任务过拟合、只依赖 trajectory 反馈、不同 Harness 组件一起优化导致互相干扰。它引入三部分：
  1. **Constrained evolution**：只允许 task-agnostic 的 Harness 修改，先限制搜索空间；
  2. **Proactive feedback**：除轨迹结果外，让 Agent 主动报告自己使用 Harness 时遇到的问题；
  3. **Component-wise optimization**：Prompt、工具、上下文/执行组件先分别优化，再合并，减少组件间干扰。
- **为什么重要**：如果让 Agent 根据少量 SWE-bench 任务直接修改自己的 Prompt、工具和运行时，很容易学出只对那批任务有效的“捷径”。这和传统 ML 的 validation/test overfitting 没本质区别，只是过拟合对象从模型参数变成了整个 Harness。
- **结果**：论文报告在 SWE-bench Verified 上，以 GPT-5.4 为 base model，HarnessCompass 在 5 轮演化后把 Pass@1 从 54% 提升到 66%，并且在 held-out tasks 与其他 base model 上保持更好的迁移表现。
- **开发者启发**：如果你以后让 Coding Agent 自动修改自己的 Prompt、tool schema、context policy 或 stop condition，一定要设立 **generalization gate**。不能因为训练任务分数上涨就立即上线；至少要在未参与演化的仓库、任务类型和模型上复测。

一个更安全的 Harness 自优化流程：

```text
Sample Tasks
   ↓
Collect Trajectory + Agent Feedback
   ↓
Propose Harness Changes
   ↓
Component-wise Evaluation
   ↓
Held-out Generalization Gate
   ↓
Merge / Reject
```

  - 论文: https://arxiv.org/abs/2608.01918
  - Elvis Saravia, AI Agents Weekly (2026-08-08): https://nlp.elvissaravia.com/p/ai-agents-weekly-agent-plugins-standard

## 今日判断

今天这四项放在一起，可以看到一个非常明确的方向：**Agent 工程正在从“单模型能力竞争”转向“可移植扩展 + 长程训练环境 + 原生交互 + Harness 自优化”**。

```text
Portable Plugins
      ↓
Agent Harness
      ↓
Frontier / Vertical Model
      ↓
Native Computer / Tool Interaction
      ↓
Executable Verification
      ↓
Harness Evolution
      ↓
Held-out Generalization Gate
```

其中最值得普通开发者立即行动的不是训练 2T 模型，而是两件事：

1. **插件与工具接口标准化**：把自己的 Skills、MCP、工具描述做成可复用资产，而不是绑定一个客户端；
2. **把验证器当核心基础设施**：代码任务用测试/CI，GUI 任务用状态检查，数据任务用 schema/结果验证。只有反馈可验证，Agent 才有机会真正长期运行和自我改进。
