## 1. Declarative Attention：让模型自己声明“这一步应该看哪里”

- **标签**：`LLM` `Long Context` `Inference` `Agent Infra`
- **论文**：*Language Models Can Control Their Own Attention*
- **arXiv**：<https://arxiv.org/abs/2609.02737>
- **提交日期**：2026-09-02

### 核心观点

长上下文模型即使最终只关注少量 token，在生成每个新 token 时，很多全局注意力层仍需要扫描完整 KV Cache。Declarative Attention（DA）不再额外训练一个检索器，而是让模型在推理文本中显式声明三种模式：

- `<global>`：读取完整上下文；
- `<focus>`：只读取指定区域；
- `<local>`：只读取最近生成内容。

推理引擎把这些声明当成类似 Tool Call 的控制信号，从而跳过绝大多数不需要的 KV Cache 读取。

论文在 15 个长上下文任务上对现成模型进行 zero-shot 测试：

- Gemma-4-31B 的 attended tokens 减少 **52.0%**；
- Qwen-3.6-27B 减少 **31.1%**；
- 平均准确率代价约 **1.27 / 2.75 个百分点**。

### 为什么重要

现在很多长上下文优化都在“模型外部”做检索、摘要或 proxy scoring，但这些方案本身仍有额外计算和系统复杂度。DA 提供了另一条路线：

> **模型本来就在推理“我现在需要什么”，那就让它把这个判断暴露给 Runtime。**

这与 Function Calling 很像：不是让模型直接执行工具，而是让模型产生结构化控制信号，再由底层系统执行。

### 对开发者的实际启发

即使今天不修改推理引擎，也可以借鉴这个思想，把 Agent 的 Context Access 显式化：

```text
Agent Step
  ↓
声明所需上下文范围
  ├─ recent_logs
  ├─ file:PlayerController.cpp
  ├─ commit:abc123
  └─ full_project_state
  ↓
Runtime 只装载对应信息
```

对于大型代码仓库 Agent，比起“每轮把 200K token 历史全部带上”，更值得做的是让模型先产生一个 **Context Access Plan**。

## 2. Harness-of-Harness：长期 Coding Agent 的关键不是一次跑更久，而是反复重启在可验证状态上

- **标签**：`Coding Agent` `Harness` `Software Engineering`
- **论文**：*Harness-of-Harness: Multi-Day Autonomous Software Development with Continual Improvement*
- **arXiv**：<https://arxiv.org/abs/2609.01481>
- **项目**：<https://github.com/Flesymeb/HarnessOfHarness>
- **提交日期**：2026-09-01

### 核心观点

Harness-of-Harness（HoH）不是替换 Codex、OpenCode 等现有 Coding Harness，而是在外面再包一层长期循环，把软件开发拆成重复的：

```text
Project Planner
    ↓
Developer
    ↓
QA Tester
    ↓
Evidence Bundle
    ↓
下一轮重新规划
```

关键不是角色数量，而是三个设计：

1. **把长期任务切成小而可验证的增量**；
2. **实现时测试与独立 QA 分离**，避免 Agent 用自己写的测试给自己打分；
3. **下一轮从版本化产物和测试证据继续，而不是依赖越来越长的聊天 transcript**。

论文在 GameCraft-Bench、FrontierSWE、ProgramBench 上，用三组不同 Harness/Model 组合测试，三轮后相对 standalone harness 平均提升 **52.25%**，最高 **82.86%**。作者还进行了超过 70 次迭代的多日实验，自动构建了一个可玩的 FPS 游戏。

### 为什么重要

这说明“长期 Coding Agent”不一定需要一个永不结束的超级 Session。

更可靠的模式可能是：

> **短生命周期 Agent + 长生命周期 Project State。**

Agent 可以不断重新初始化，只要代码、测试、计划、缺陷和版本历史是持久且可验证的。

### 对开发者的实际启发

如果要让 Agent 连续工作数小时甚至数天，优先设计：

```text
project_state/
├─ requirements.md
├─ current_plan.md
├─ qa_report.json
├─ known_failures.md
├─ test_results/
└─ git_history
```

而不是把“上下文窗口够大”当成主要解决方案。

同时把 **开发测试** 与 **验收测试** 分开。实现 Agent 不应该拥有完整的验收判定权。

## 3. SKILL.state：长程 Agent 应保存“状态”，而不是保存全部思考过程

- **标签**：`Agent` `State` `Context` `Efficiency`
- **论文**：*SKILL.state: Scalable Long-Horizon Agent Skills*
- **arXiv**：<https://arxiv.org/abs/2608.26263>

### 核心观点

很多 Agent Runtime 的默认结构是 append-only：

```text
Observation 1
Reasoning 1
Action 1
Observation 2
Reasoning 2
Action 2
...
```

任务越长，Prompt 越长，延迟和成本持续增加，而且旧推理错误还可能污染后续决策。

SKILL.state 直接换掉这个抽象：每一步只保留三类东西：

```text
Immutable Skill Spec
+ Current Structured State
+ Latest Observation
```

模型完成一步推理后，输出一个经过验证的 JSON Patch 来更新状态；中间 reasoning 随即丢弃。

因此 Prompt 大小从随步骤数增长的 **O(T)**，变为近似 **O(1)**。

### 为什么重要

这和传统软件系统的 Event Log / State Machine 非常接近。Agent 的“思考过程”只是计算中间量，并不一定值得永久进入上下文。

真正应该跨步骤保存的是：

- 当前目标；
- 已完成事项；
- 未解决阻塞；
- 关键变量；
- 工具结果；
- 必要约束。

而不是模型为得到这些结论生成的全部自然语言推理。

### 对开发者的实际启发

可以把 Agent Session 从：

```text
conversation = conversation + everything
```

改成：

```text
state = validate(patch(state, model_output))
```

对于 Coding Agent，一个执行状态可以类似：

```json
{
  "goal": "fix multiplayer reconnect bug",
  "files_touched": ["NetDriver.cpp"],
  "tests_passed": ["ReconnectTest"],
  "tests_failed": [],
  "open_questions": ["dedicated server path"],
  "next_action": "inspect reconnect timeout branch"
}
```

这通常比保存几十万 token 的工作日志更稳定。

## 4. CORAL：真正进入生产环境的 Agent，核心能力是“在约束预算内持续优化”

- **标签**：`Agent` `Production` `Optimization` `Guardrails`
- **论文**：*CORAL: An LLM-Native Harness for Production Recommender Systems*
- **arXiv**：<https://arxiv.org/abs/2609.02730>
- **提交日期**：2026-09-02

### 核心观点

Meta 的 CORAL 把 Agent 放进真实推荐系统的持续闭环：

```text
Observe
  ↓
Reason over past decisions
  ↓
Optimize
  ↓
Deploy bounded change
  ↓
Measure A/B outcome
  ↓
写回 memory
```

Agent 会读取线上运行信号、历史决策与结果，并调用包括数值优化器在内的工具重新配置推荐系统。

最重要的部分不是 LLM，而是 **constrained optimizer**：任何改动都必须保持在固定 operating budget 内，Agent 没有无限制修改系统的权限。

论文报告，同一个 Harness 在两个大型社交平台上分别实现：

- 在不增加 serving cost 的情况下提升 engagement；
- 在不降低 engagement 的情况下减少 serving cost。

### 为什么重要

很多“自动优化 Agent”只在离线 Benchmark 中成立，因为生产环境真正的问题不是“能不能找到更优参数”，而是：

> **你敢不敢让它改生产系统？**

CORAL 给出的答案不是让模型更谨慎，而是把 Agent 的自由度限制在数学可验证的预算内。

### 对开发者的实际启发

高风险 Agent 不应该直接拥有 unrestricted write access。可以把它改成：

```text
Agent Proposal
      ↓
Constraint Solver / Policy Engine
      ↓
Allowed Delta
      ↓
Canary / A-B Test
      ↓
Measured Result
      ↓
Rollback or Promote
```

这比在 System Prompt 里写“请谨慎修改生产系统”可靠得多。

## 5. AI Research Preference Models：昂贵 Agent 的下一步不是更会生成方案，而是更会放弃方案

- **标签**：`Research Agent` `Planning` `Compute Efficiency`
- **论文**：*AI Research Preference Models*
- **arXiv**：<https://arxiv.org/abs/2608.13940>

### 核心观点

自动科研 Agent 很容易生成几十个实验想法，但 GPU 预算只够真正跑其中少数几个。Meta 团队训练 **Research Preference Model（RPM）**，专门预测哪个候选方案更值得投入完整实验成本。

论文提出两个版本：

- **Inference-only RPM**：只看候选计划、代码和搜索树中已有实验结果；
- **Agentic RPM**：允许先运行便宜的小规模 pilot experiment，再决定是否投入完整预算。

集成到 AIRA-dojo 后，平均 normalized score 从 **0.684** 提升到 **0.711 / 0.729**；两种方法都能在大约 **15 小时**达到 unguided agent 需要 **24 小时**才能达到的水平，同时使用不到其三分之二的执行预算。

### 为什么重要

Agent 的搜索空间会随着工具能力快速膨胀。未来瓶颈往往不是“想不到下一步”，而是：

> **候选下一步太多，而每一步真实执行都很贵。**

因此“是否值得执行”本身会成为一个独立模型问题。

### 对开发者的实际启发

Coding Agent 同样可以引入轻量级 proposal ranking：

```text
生成 5 个修复方案
   ↓
Cheap evaluator
   ├─ 修改范围
   ├─ 风险
   ├─ 可测试性
   ├─ 历史相似结果
   └─ 预计成本
   ↓
只执行 Top-1 / Top-2
```

对于需要编译大型项目、运行 GPU 实验或操作真实云资源的 Agent，这种“执行前筛选”通常比让主模型多思考几千 token 更值钱。

## 6. Trace as State：同一段推理，放在长上下文前面还是后面，可以差几十个百分点

- **标签**：`Reasoning` `Long Context` `Context Engineering`
- **论文**：*Trace as State: Reasoning Traces as Conditional States for Long-Context Transformers*
- **arXiv**：<https://arxiv.org/abs/2609.02702>

### 核心观点

因果 Transformer 从左到右处理上下文。如果模型在读完大量内容后才推导出“任务真正的状态是什么”，这个状态无法反过来影响它已经完成的前半段读取。

Trace as State 的做法很简单：

1. 第一遍阅读并产生 reasoning trace；
2. 开一个 fresh pass；
3. 把 reasoning trace 放在长上下文 **前面**；
4. 再让模型读取原始长上下文。

作者用相同 trace 放在上下文后面的 Trace Append 作为控制变量。Trace as State 在 27 个 model-task-metric 组合中赢了 **26 个**。

在 GraphWalks Parents 上：

- DeepSeek V4 Pro Preview：29.2% → append 43.0% → **Trace as State 81.8%**；
- GLM-5.2：66.4% → append 83.2% → **Trace as State 100%**。

### 为什么重要

Context Engineering 不只是“放哪些内容”，还包括：

> **这些内容以什么因果顺序进入 Transformer。**

相同信息在 Prompt 尾部和 Prompt 头部可能有完全不同的效果。

### 对开发者的实际启发

对长代码库分析，可以尝试两阶段工作流：

```text
Pass 1：扫描代码 → 生成 compact task state

Pass 2：
[task state]
[关键假设]
[当前怀疑路径]
[完整代码/检索结果]
→ 最终分析
```

这和简单地在末尾追加“这是我刚才的思考”不同。关键是让已推导出的状态成为下一次读取的**条件**。

## 7. Selective Forgetting：Graph Memory 不一定优于向量检索，但“适度遗忘”可能几乎免费

- **标签**：`Memory` `Agent` `RAG`
- **论文**：*Selective Forgetting: A Graph-Based Memory Framework for Long-Term LLM Agents*
- **arXiv**：<https://arxiv.org/abs/2608.28978>
- **代码**：<https://github.com/skhanzad/Selective-Amnesia>

### 核心观点

这篇论文最值得注意的是一个**负结果**。

在 LongMemEval 上，当候选生成预算固定为 5 个 retrieval roots 时：

- Graph Memory token F1：**0.417**；
- Flat Vector Retrieval：**0.468**。

差距最大的是需要精确回忆某个历史 assistant turn 的问题：judged correctness 从向量检索的 **0.911** 降到图结构的 **0.607**。

原因很直观：把一整段对话拆成实体和关系后，虽然结构变好了，但原始措辞、局部上下文和 surface form 可能被丢掉。

反而论文里的 forgetting module 表现不错：对一个 27,021 节点的持久图做一次 pruning，删掉约 **9.8% 节点 / 9.5% 字节**，token F1 基本不变。

### 为什么重要

近两年很多 Agent Memory 系统默认：

```text
Vector Store < Knowledge Graph
```

但这篇论文提醒我们：**结构化不是免费的。**

把原始记录强行转成图，会引入不可逆的信息损失。Memory 架构应该根据问题类型选，而不是默认越复杂越好。

### 对开发者的实际启发

长期 Agent 更适合采用混合记忆：

```text
Raw Event / Conversation Store   ← 保留原始证据
Vector Index                     ← 模糊检索
Graph / Entity Index             ← 关系查询
Selective Forgetting             ← 删除低价值派生结构
```

Graph 应该是索引，不应该成为唯一事实来源。

## 今日判断：Agent 的新核心是“显式状态 + 可约束执行 + 计算预算分配”

把这七篇放在一起，可以看到非常一致的架构迁移：

```text
过去：
Long Prompt
+ Big Model
+ Tool Loop

现在：
Context Access Plan
+ Explicit State
+ Iterative Harness
+ Independent QA
+ Proposal Ranking
+ Constraint Solver
+ Persistent Raw Memory
```

其中最值得马上落地的三个变化是：

1. **把长期 Agent 的核心状态从聊天记录里拆出来**：使用结构化 state，而不是 append-only transcript；
2. **把昂贵动作放到候选筛选之后**：编译、训练、部署、网页写操作都先经过 cheap ranking / validation；
3. **不要让 LLM 自己承担生产安全边界**：真正的修改范围、预算和回滚规则交给确定性系统。

从开发实践看，这些改动往往比单纯更换下一代模型更稳定，而且能跨模型复用。
