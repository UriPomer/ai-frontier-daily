## 1. Skaling：模型规模和数据量并不是彼此独立的两个旋钮

- **标签**：`Scaling Law` `Pretraining` `LLM` `Efficiency`
- **论文**：*Skaling: Chinchilla's Exponents Meet Kaplan's Coupling*
- **提交日期**：2026-08-07
- **论文**：<https://arxiv.org/abs/2608.07222>

### 核心观点

经典 Chinchilla scaling law 通常把模型参数量 `N` 和训练数据量 `D` 对 loss 的影响写成两个相加、彼此独立的项。这个形式很简洁，但也隐含了一个强假设：

> 改变模型规模时，数据规模的边际作用不变；改变数据规模时，模型规模的边际作用也不变。

Skaling 认为这个假设在现实训练区间并不成立，尤其是在两个越来越重要的区域：

- **data-scarce**：数据不够、模型相对偏大；
- **heavy-overtraining**：模型固定，但训练 token 远超过经典 compute-optimal 点。

论文通过加入一个单独的 **interaction exponent**，显式建模 `N` 和 `D` 的耦合，而不是把两者完全拆开。

作者报告：

- 在 interpolation 和 extrapolation 上，MAPE 下降约 **1.5–3 倍**；
- 在测试配置中，Skaling 在约 **76%** 的配置上优于传统形式；
- 配合一个只在低算力区域采样的 **L-shape sparse grid**，可以用大约 **1/10 的 profiling compute** 推断完整训练网格。

### 为什么重要

Scaling law 不是纯理论工具，它直接参与非常昂贵的训练预算决策：

```text
小规模实验
  ↓
拟合 scaling law
  ↓
预测更大模型 / 更多 token 的 loss
  ↓
决定正式训练预算
```

如果函数形式在边缘区间系统性偏差，那么最终可能不是“预测差一点”，而是：

- 错估应该增加参数还是增加 token；
- 错估一个模型是否值得继续 overtrain；
- 用错误的最优点分配几百万美元甚至更多训练预算。

尤其是现在很多团队已经不再严格按照 Chinchilla compute-optimal 训练，而是倾向于**更小模型 + 更多 token**以降低推理成本，传统 scaling law 的外推误差会变得更实际。

### 对开发者 / 训练工程师的实际启发

如果在做自己的预训练或 domain-adaptive pretraining，不要默认：

```text
loss = model_size_effect + data_effect
```

更稳妥的做法是至少检查 `N × D` 是否存在明显 interaction。

如果算力预算有限，可以借鉴论文的思路，不一定要跑完整二维网格：

```text
固定小数据 → sweep model size
固定小模型 → sweep data size
        ↓
用稀疏边界点拟合耦合项
        ↓
外推完整 compute grid
```

这对于中小团队尤其重要，因为真正昂贵的不是单次训练，而是为了拟合 scaling law 再额外跑几十个 profiling model。

### 一个更广泛的启发

这篇论文也提醒我们：**经验 scaling law 的函数形式本身就是模型假设。**

不要因为某个公式已经被广泛使用，就把它当作物理定律。对于新的训练分布、长上下文模型、MoE、超量 token 训练或多阶段训练，最好重新验证它的残差结构，而不是只重新拟合参数。

## 2. Cracks in the Foundation：短上下文训练看不出来的问题，可能在扩展长上下文时一起爆发

- **标签**：`Long Context` `Architecture` `Transformer` `Pretraining`
- **论文**：*Cracks in the Foundation: Seemingly Minor Architectural Choices Impact Long Context Extension*
- **提交日期**：2026-08-10
- **状态**：COLM 2026 接收
- **论文**：<https://arxiv.org/abs/2608.10296>

### 核心观点

这篇论文研究的不是一种全新架构，而是一个更容易被忽略的问题：

> 传统 dense Transformer 里一些看似“只是工程取舍”的小设计，会不会决定以后能不能顺利扩展到长上下文？

作者固定训练数据、tokenizer 和 context-extension recipe，只改变四类架构设计：

- normalization；
- GQA；
- pretraining context length；
- sliding-window attention。

这些设计都至少出现在 OLMo、Llama、Qwen 等主流 dense model 家族中。

结论非常值得警惕：

- 单独一个设计通常只造成小幅下降；
- **三个或更多不利选择组合起来时，长上下文 downstream performance 最多可下降 47%**；
- 这种问题在**短上下文 loss 和常规 validation set 上基本看不出来**；
- 但如果在 pretraining 早期就做 context extension probe，可以更早发现这些结构性差异。

作者为此训练了超过 **170,000 GPU hours**，并发布 **OlmPool**：26 个可比较的 7B 模型，包含 context extension 前后的 checkpoint。

### 为什么重要

很多团队的模型开发流程是：

```text
先训练一个短上下文模型
      ↓
看 loss / benchmark 不错
      ↓
后期通过 RoPE scaling / continued pretraining 扩到 128K、1M
```

这篇论文说明：

> 你在第一阶段“看不见”的架构债务，可能会在第二阶段长上下文扩展时集中爆发。

这和传统软件里的技术债很像：短期 benchmark 看起来没问题，但架构本身已经限制了未来扩展性。

### 对开发者的实际启发

如果你的应用强依赖长上下文，不要只看模型发布时标称的 `context_window=128k/1m`。

更应该看：

- Needle / retrieval 之外的真实 long-context downstream task；
- context length 增长后性能曲线是否平滑下降；
- 长上下文 fine-tune / continued pretraining 后是否真的恢复能力；
- 模型架构是否大量使用局部 attention 或其他可能限制远程信息传播的机制。

如果你在训练自己的模型，则可以把 **early context-extension probe** 变成架构选择阶段的单元测试：

```text
训练早期 checkpoint
      ↓
小规模扩展 context
      ↓
跑 long-context probe
      ↓
发现结构缺陷后尽早淘汰
```

这比模型完整训练完再发现“128K 只是能塞进去，但不能真正用”便宜得多。

### 对 Agent 开发的额外意义

Agent 越来越依赖大 context 保存：

- repository state；
- tool result；
- browser history；
- memory；
- multi-agent communication。

因此长上下文能力不能只理解为“模型支持更大的 token limit”。真正重要的是：

> 当上下文从 16K 增长到 128K / 1M 时，模型还能不能稳定找到、组合并利用早期信息。

这篇论文提醒开发者，模型架构本身可能决定这种能力的上限。

## 3. CEDAR：LLM Agent 不只搜索答案，也开始搜索“系统结构”

- **标签**：`Agent` `Search` `MCTS` `Complex Systems` `Scientific AI`
- **论文**：*CEDAR: Agent-Orchestrated Tree Search for Goal-Directed Optimization of Complex Systems*
- **提交日期**：2026-08-07
- **状态**：ALIFE 2026 Talk
- **论文**：<https://arxiv.org/abs/2608.06871>

### 核心观点

很多优化问题默认结构已经固定，算法只负责调参数：

```text
固定系统结构
  ↓
搜索参数
  ↓
寻找更优结果
```

CEDAR 反过来搜索**系统本身的反馈结构**。

它把复杂系统表示成一个受限、可执行的 Python 子集，然后让两个 LLM 角色参与 Monte Carlo Tree Search：

```text
当前系统
  ↓
LLM Editor：提出结构修改
  ↓
运行模拟
  ↓
LLM Judge：根据目标评价 emergent behavior
  ↓
MCTS 决定下一步搜索方向
```

这里：

- Editor 类似 evolutionary search 中的 mutation / variation operator；
- Judge 类似 fitness function；
- MCTS 负责在不同结构分支之间分配搜索预算。

与单纯让 LLM “自由改代码直到变好”相比，CEDAR 把搜索过程放进了一个显式 tree search 框架，并保留多个不同候选结构，避免过早收敛到单一路径。

### 为什么重要

这代表 Agent 搜索空间正在发生变化。

过去常见：

```text
搜索 prompt
搜索 tool sequence
搜索参数
搜索代码 patch
```

现在开始变成：

```text
搜索系统拓扑
搜索反馈关系
搜索算法结构
```

也就是说，LLM Agent 的价值不只是“更聪明地执行一个已有流程”，而是**参与设计流程本身**。

这和近期 Harness Evolution、AutoML、AI Scientist 的趋势其实是一条线：

> 把人工定义的系统组件变成 Agent 可以编辑和验证的搜索对象。

### 对开发者的实际启发

如果某个问题满足下面三个条件，就可以考虑结构搜索而不是只调参数：

1. 系统可以被写成**可执行程序**；
2. 结果可以被**自动模拟 / 测试**；
3. 有一个相对可靠的**目标函数 / Judge**。

比如游戏开发中就有不少潜在场景：

```text
经济系统参数与反馈结构
NPC 群体行为规则
资源循环
自动平衡机制
战斗数值系统
关卡生成规则
```

传统做法往往是设计师固定公式，只调整数字；CEDAR 类方法则允许 Agent 修改“公式和反馈关系本身”，然后通过模拟筛选。

但生产使用时，Judge 最好尽可能**确定性 / 可验证**。如果 Editor 和 Judge 都只是同一个 LLM 的主观判断，很容易出现 reward hacking 或自我说服。

更稳妥的模式是：

```text
LLM 提案
  ↓
确定性 simulator / test
  ↓
数值指标
  ↓
LLM 只负责解释与下一步搜索
```

## 今日判断

今天补充的三篇论文分别来自训练、架构和 Agent 搜索，看起来跨度很大，但有一个共同点：

> **真正重要的 AI 工程问题，越来越发生在“系统级结构”而不是单次模型调用上。**

Skaling 说明训练规划里，模型和数据不能被简单当成独立变量；Cracks in the Foundation 说明模型架构里，小设计会决定未来长上下文的可扩展性；CEDAR 则进一步把“结构本身”变成 Agent 可以搜索的对象。

可以把这个趋势概括成：

```text
过去：
调参数 → 看分数

现在：
验证假设
  ↓
选择结构
  ↓
自动搜索 / 模拟
  ↓
持续评估可扩展性
```

对开发者最实际的启发是：**不要只优化当前 benchmark；要把“以后还能不能扩展”也变成今天的测试指标。**
