## 1. Jev：一种专门给软件做“快速决策”的 System One Model

- **标签**：`Model Architecture` `Agent Infra` `Routing` `Verification`
- **发布方**：TypeSafe AI
- **发布日期**：2026-09-15
- **官方介绍**：<https://typesafe.ai/blog/introducing-system-one-models-and-jev>

### 核心观点

TypeSafe 把现有聊天式 LLM 称为偏“System Two”的模型：输入自然语言，模型逐 token 生成字符串，灵活但慢、昂贵，而且软件还要负责解析与校验输出。

Jev 反过来放弃开放式文本生成，只做三类**预先定义输出空间的决策**：

- Boolean：某件事为真的概率；
- Choice：从给定选项中选择；
- Score：输出指定范围的分数。

每个输出都会附带概率 / 置信度。TypeSafe 称它的训练方法为 **Reinforcement Learning for Calibrated Decisions（RLCD）**，并强调所有结果并行生成，而不是 autoregressive decoding。

官方公布的定价与延迟为：

- 输入：**$0.042 / 1M tokens**；
- 输出：不按生成 token 计费；
- 端到端延迟约 **70–500 ms**。

TypeSafe 还宣称在其内部工作流上能达到相对于 frontier LLM 数十到数百倍的速度 / 成本优势，但这些性能对比目前主要来自厂商自己的评测，应该视为待独立验证的结果。

### 为什么重要

Jev 真正值得关注的不是某个 benchmark，而是**模型接口的变化**。

过去我们经常这样调用 LLM：

```text
状态 / 日志
   ↓
Prompt
   ↓
LLM 生成 JSON
   ↓
Parser
   ↓
Schema Validator
   ↓
重试 / 修复
```

Jev 提出的方向更接近：

```text
状态
 + Typed Question
      ↓
Decision Model
      ↓
Typed Probability
```

如果这种模型类别成立，未来 Agent Stack 可能不会只有一个“大模型”，而是：

```text
生成 / 复杂规划  → Frontier Reasoning Model
路由 / 分类       → Fast Decision Model
安全检查           → Safety Model
Judge / Verification → Decision / Reward Model
```

### 对开发者的实际启发

不要默认所有 AI 决策都必须走聊天模型。

对于下面这些高频、结构确定的环节，应该单独测量是否值得换成轻量决策模型：

- 选择下一种 Tool；
- 判断是否需要 Web Search；
- 按优先级路由 Bug；
- 判断一个 Agent 输出是否值得继续执行；
- Safety / Guardrail；
- 选择模型或子 Agent；
- 给几十万个日志事件做标签。

尤其对于高频 Agent，**每一步少几百毫秒和几千 token，乘上百万次调用以后就是系统级差距**。

同时需要避免一个概念混淆：Jev 的“不会 hallucinate”更准确地说是**不会生成类型空间之外的值**，不代表分类或判断不会出错。生产系统仍然需要阈值、校准和回退策略。

## 2. Salesforce Koa：企业 Agent 的后训练开始围绕“工作流规范”而不是普通指令数据

- **标签**：`Enterprise Agent` `Tool Use` `RL` `Open Weights`
- **论文**：*Salesforce Koa: An Enterprise Language Model for Agentic Tool Use*
- **arXiv**：<https://arxiv.org/abs/2609.15066>
- **Salesforce 公告**：<https://investor.salesforce.com/news/news-details/2026/Announcing-Koa-Salesforces-First-CRM-Reasoning-Model-Built-on-NVIDIA-Nemotron/default.aspx>

### 核心观点

Koa 是 Salesforce 基于 **NVIDIA Nemotron-3-Super-120B** 继续后训练的 CRM Agent 模型。它最有意思的部分不是 120B 参数，而是训练数据生成方式。

Salesforce 把企业工作流写成规范，再将规范扩展为：

```text
Workflow Specification
      ↓
Persona-conditioned Task
      ↓
Multi-turn Environment
      ↓
Tool Calls
      ↓
Task Resolution Reward
      ↓
GRPO
```

内部企业规范来自 **Agent Script**，公共工具任务则通过合成工作流结构生成。

Koa 的训练只使用公开数据与合成数据，Salesforce 明确表示**没有使用客户数据**。公开结果显示，它相对 Nemotron 基座在 BFCL、Tau2Bench 和 Salesforce CRM Bench 上都有提升，其中最明显的是多轮工具调用能力。

### 为什么重要

很多企业 Agent 项目最大的误区是：

> 收集很多“好问答” → SFT → 希望模型自动学会业务流程。

Koa 更像是在训练**可执行流程能力**：

- 哪一步该调用什么工具；
- 什么条件下应该继续；
- 数据依赖有没有满足；
- 什么时候任务才真正完成。

它把企业 SOP / Workflow Specification 直接变成 Agent RL 的训练源。

### 对开发者的实际启发

如果你要做垂直 Agent，与其先攒聊天记录，不如先把现有业务流程结构化：

```yaml
workflow: refund_order
preconditions:
  - order.exists
  - user.identity_verified
steps:
  - inspect_payment
  - check_refund_policy
  - create_refund
success:
  - refund.status == accepted
failure:
  - policy_violation
```

这种规范同时可以用来：

- 合成训练任务；
- 生成环境模拟器；
- 做 reward；
- 做 Agent eval；
- 做生产 guardrail。

**工作流规范很可能会成为企业 Agent 的“源代码”。**

## 3. Periodic Neon：下一阶段 AI Scaling 的数据源可能来自物理实验，而不是互联网

- **标签**：`AI for Science` `RL` `Data Flywheel` `Infrastructure`
- **发布方**：Periodic Labs
- **官方 News**：<https://periodic.com/news>
- **研究主题**：*Nature Is Our Learning Environment*

### 核心观点

Periodic Labs 发布了 **Periodic Neon**，一个基于约 1T 参数开放权重模型 Kimi K2.6 继续做 scientific mid-training 和 RL 的材料科学模型。

它已经被部署到 Periodic 自己的高通量材料实验室，用来分析 **X-ray diffraction（XRD）** 实验结果。

其内部 FrontierXRD 评测包含 134 个复杂真实实验样本；官方报告：

- 基座 Kimi K2.6：**2.7%** 成功率；
- Neon：**55.3%**；
- 并宣称在同一 Periodic Harness 下超过 GPT-6 Astra 与 Claude Fable 5.1。

最终 mid-training + RL 阶段峰值使用约 **1,300 张 H200**。

但这些结果需要谨慎解读：Benchmark、Harness 和 Judge 主要由 Periodic 自己构建，目前缺乏独立复现。Neon 也不是从零预训练出的 1T 模型，而是建立在已有开放权重模型上继续训练。

### 为什么重要

真正有价值的是它的数据飞轮：

```text
实验室产生真实数据
      ↓
模型学习
      ↓
模型分析实验
      ↓
决定更值得做的实验
      ↓
实验室产生更多新数据
```

过去 Scaling 的“燃料”主要是网页、代码、书籍和合成数据；Periodic 的赌注是：

> **物理世界本身可以变成持续产生新训练数据的 Environment。**

如果未来互联网高质量文本继续接近饱和，那么拥有可自动化实验环境的人，会拥有别人无法直接下载的数据源。

### 对开发者的实际启发

这件事不仅适用于材料科学。

任何存在**可执行环境 + 可观测结果 + 可验证目标**的领域，都可以建立类似飞轮：

```text
Simulation / Real Environment
        ↓
Agent Action
        ↓
Measured Outcome
        ↓
Reward / New Dataset
        ↓
Post-training
```

游戏尤其天然适合这种结构：游戏引擎本身就是一个高速、可重复、可验证的世界模型环境。NPC 行为、关卡策略、经济系统和 QA Agent 都可以把游戏运行结果反过来做训练信号。

## 4. Anthropic 公布 AI R&D 自动化指标：Claude 已“主导”26% 的测量任务，但还没有真正完全自治

- **标签**：`AI R&D` `Self-Improvement` `Agent Safety` `Metrics`
- **官方报告**：<https://www.anthropic.com/institute/measuring-pace-of-ai-development>

### 核心观点

Anthropic 开始尝试量化 AI 在自身模型研发中的实际参与程度。

它采用 AL0–AL5 的自动化等级：

- AL3：AI 与人类深度协作；
- AL4：AI 从高层 Prompt 出发，能够主导大部分任务，人在监督；
- AL5：完全自治、无人在环。

截至 **2026 年 8 月**，Anthropic 报告：

- Claude 在其测量范围内**主导约 26% 的 AI R&D 工作**；
- 超过 **90%** 的工作至少达到深度 AI 协作；
- **没有任何被测子集达到完全自治**；
- 在其最常用的内部平台上，大约有 **30,000 个 Agent 同时从事研究与工程工作**。

Anthropic 同时描述了两层监控：

- Online Monitor：实时阻止不可逆危险行为；
- Offline Monitor：事后审计慢性风险和异常模式。

### 为什么重要

“AI 会不会帮助训练下一代 AI”已经不是纯理论问题，真正重要的是**速度如何测量**。

一个 frontier lab 如果不能量化：

- AI 完成了多少工作；
- 人类还在哪些环节是瓶颈；
- Agent 自主程度提升得多快；
- 高风险操作中 AI 占比多少；

就很难判断研发加速是否正在形成自我强化循环。

### 对开发者的实际启发

企业内部使用 Agent 时，也应该建立“自动化成熟度”而不是只看 token 用量。

可以记录：

```text
L0：纯人工
L1：AI 提建议
L2：AI 完成小任务，人确认
L3：AI 完成大块工作，人持续指导
L4：AI 主导任务，人监督结果
L5：完全自动执行
```

然后按代码、测试、文档、客服、运营等不同任务分类统计。

这样才能真正回答：

> “AI 到底替我们完成了多少工作？”

而不是只回答“团队调用了多少次模型”。

## 5. HarnessTax：同一个模型，成功率差不多，Harness 却能让成本差数倍

- **标签**：`Coding Agent` `Harness` `Cost` `Evaluation`
- **项目**：HarnessTax
- **主页**：<https://harnesstax.github.io/>

### 核心观点

UC Berkeley Sky Lab 与 Arena 团队测试了：

- 7 个模型；
- 3 个 Coding Harness：Claude Code、Codex CLI、Pi；
- SWE-bench Lite 与 Terminal-Bench 2.0；
- 每种模型 × Harness 组合各跑相同任务。

核心结果不是“谁赢”，而是：

> **Harness 对成功率的平均影响相对有限，但对成本的影响非常明显。**

例如在 SWE-bench Lite 上，Claude Fable 5：

- Claude Code：97.8%，约 $1.33 / rollout；
- Pi：96.7%，约 $0.67 / rollout。

研究观察到某些组合的成本可以相差最高约 **5×**。

其中一个直接原因在 Agent 开始做事前就出现了：不同 Harness 注入的 System Prompt、Tool Schema 与控制信息大小差异巨大。公开测量中，Claude Code 的初始工具 / 指令 Context 明显大于极简 Pi。

### 为什么重要

过去我们总在比较：

```text
Claude vs GPT vs Gemini
```

现在更合理的比较单位是：

```text
Model × Harness × Tools × Context Policy × Stop Condition
```

相同模型并不等于相同系统。

### 对开发者的实际启发

如果一个 Agent 每天跑很多次，先 Profile 下面这些东西：

```yaml
initial_context_tokens:
tool_schema_tokens:
avg_turns:
avg_tokens_per_turn:
compaction_count:
tool_calls:
cost_per_success:
wall_clock_per_success:
```

尤其要小心 MCP / Plugin 越接越多以后，**所有 Tool Schema 都可能成为每轮固定税负**。

不要只测“能不能完成任务”，同时测：

> **每个成功任务到底花了多少钱。**

## 6. Claude Code Projects + Devin Code Scans：Coding Agent 正从单线程助手变成并行工程组织

- **标签**：`Coding Agent` `Multi-Agent` `Orchestration`
- **Claude Projects**：<https://claude.com/blog/projects-redesigned>
- **Devin Code Scans**：<https://devin.ai/blog/introducing-code-scans>

### Claude Code Projects

Anthropic 在 9 月 17 日重做了 Claude Code Projects。

现在一个 Project 不再只是“文件夹 + 对话”，而是：

```text
Project Coordinator
   ├─ Thread A → 独立 Claude Code cloud session / branch
   ├─ Thread B → 独立 Claude Code cloud session / branch
   └─ Thread C → 独立 Claude Code cloud session / branch
```

Coordinator 负责：

- 拆任务；
- 创建并行 Thread；
- 跟踪结果；
- Review 输出；
- 组织最终交付。

每个 Thread 都是完整的云端 Claude Code Session，拥有自己的 repo copy 和 branch；Project 还提供共享 Memory 与 Artifact Library。

Anthropic 同时提醒，Thread 越多，Usage 消耗越快；如果修改同一份代码，依然会像普通 Git 分支一样出现 merge conflict。

### Devin Code Scans

Cognition 的 Code Scans 解决的是另一种工程任务：

> “我知道目标，但不知道该改哪些地方。”

例如：

- 降低维护成本；
- 提升 SEO；
- 提高编译速度；
- 找出整个代码库的清理机会。

它使用 **Agentic MapReduce**：把大型代码库调查拆成批次，交给多个 Agent 并行扫描，再汇总成一份发现报告并进一步生成 PR。

### 为什么重要

这两种产品其实代表了两个不同的 Agent 并行范式：

```text
Claude Projects：
Goal → 多个独立工程任务 → 多 Branch → PR

Devin Code Scans：
Large Search Space → 并行扫描 → Reduce / Synthesis → Action
```

单 Agent 的长上下文并不会自动解决大型代码库问题。随着代码库扩大，**横向并行搜索与任务拆分**会变得越来越重要。

### 对开发者的实际启发

不要一上来就设计“Agent Swarm”。先判断任务属于哪一类：

- 可独立拆分的 feature / repo → 多 Worker；
- 大范围搜索 / 审计 → MapReduce；
- 强顺序依赖任务 → 单 Agent + durable state；
- 同一文件高耦合修改 → 并行往往得不偿失。

并行 Agent 的瓶颈最终通常会落到：

- shared state；
- conflict detection；
- evaluation；
- merge；
- budget allocation。

## 7. PARSER：长文档不要顺序读，先并行读，再让 Lead Agent 深度推理

- **标签**：`Long Context` `Multi-Agent` `Retrieval` `RL`
- **论文**：*PARSER: Read in Parallel, Reason in Depth for Long-Context LLM Agents*
- **arXiv**：<https://arxiv.org/abs/2609.06702>
- **项目页**：<https://cuhk-parser.github.io/>

### 核心观点

很多 Long-Context Agent 采用 Sequential Memory：

```text
Chunk 1 → 更新 memory
Chunk 2 → 更新 memory
Chunk 3 → 更新 memory
...
```

问题是：

- 延迟随文档长度线性增长；
- 前面的证据容易被后续压缩覆盖；
- 证据位置会影响准确率；
- 多跳问题中，后一个检索问题往往只有找到前一跳证据后才知道怎么问。

PARSER 把“读取”和“推理”拆开：

```text
              ┌ Reader 1 → Chunk 1
Lead Agent →  ├ Reader 2 → Chunk 2
              ├ Reader 3 → Chunk 3
              └ Reader N → Chunk N
                    ↓
                 Gather
                    ↓
              下一轮 Query
```

所有 Reader 并行、冻结、不训练；只有 Lead Agent 用 RL 学习如何发 Query、聚合证据和决定什么时候回答。

论文报告：

- 4B 模型相对最强 sequential-memory baseline 平均高 **5.7 分**；
- 在 896K token Context 下高 **12 分**；
- 9B 版本在其测试上超过 DeepSeek-V4-Pro **6.3 分**；
- 推理延迟最高降低 **11×**。

### 为什么重要

超长 Context Window 不代表模型应该把一切都放进一个串行注意力过程。

对于文档、代码库、日志和知识库，真正更自然的计算结构可能是：

> **并行读取，顺序推理。**

### 对开发者的实际启发

这非常适合：

- 大代码库架构审计；
- 多文档尽调；
- 大型日志定位；
- 多论文科研综述；
- 游戏项目 Asset / Script 全局检查。

它和 Devin Code Scans 实际上有同一个底层思想：

> **把 Search / Read 变成可扩展的并行宽度，把真正昂贵的 Reasoning 保留在一个较窄的关键路径上。**

## 8. Gemini 3.8 Live：语音 Agent 开始同时“说话、思考、调用工具”，不再轮流进行

- **标签**：`Voice Agent` `Multimodal` `Realtime`
- **Google 官方发布**：<https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-3-8-live-gemini-3-8-live-extended-thinking/>
- **开发者介绍**：<https://blog.google/innovation-and-ai/technology/developers-tools/build-real-time-voice-applications-gemini-audio/>

### 核心观点

Google 发布两档实时语音模型：

- **Gemini 3.8 Live**：面向大规模和成本效率；
- **Gemini 3.8 Live Extended Thinking**：面向复杂多步任务。

Extended Thinking 最值得注意的行为不是“想得更久”，而是**可以保持自然对话的同时进行后台 reasoning / function calls**。

也就是说交互不再是：

```text
用户说完
→ Agent 沉默
→ 思考
→ 调 API
→ 再说话
```

而可以是：

```text
用户说话
→ Agent 立即语音确认
→ 后台调用工具 / 推理
→ 持续播报进度
→ 返回结果
```

Google 报告 Extended Thinking 在 Artificial Analysis Speech-to-Speech Quality Index 上达到 82.6，并支持视觉上下文和复杂异步工具调用。

### 为什么重要

Voice Agent 过去最大的产品问题之一不是模型“不会答”，而是**工具调用期间的沉默非常不像人类交流**。

一旦 speaking、reasoning 和 tool execution 能够真正并行，语音 Agent 的交互设计会从“语音版聊天机器人”转向真正的实时协作者。

### 对开发者的实际启发

实时 Agent 的 Runtime 最好拆成三个并发通道：

```text
Audio I/O
Reasoning / Planning
Tool Execution
```

不要让一次慢 API 调用冻结整条对话链路。

对于游戏 NPC 也一样：NPC 可以先通过语音 / 动画做即时反馈，同时后台进行路径规划、知识检索或复杂策略计算，而不是站着不动等待模型完整输出。

# 本期最重要的三个判断

## 1. 大模型正在被拆成“生成模型 + 决策模型 + Judge + Safety + Router”

Jev 是目前最明显的信号之一。很多过去强行用聊天模型完成的高频判断任务，未来可能由便宜几个数量级的 Decision Model 承担。

## 2. Agent 的性能竞争正在转向系统结构，而不是模型排行榜

Koa 的 Workflow Specification、HarnessTax 的成本差异、Claude Projects / Devin 的并行编排、PARSER 的 scatter-gather 都说明：

> **Model 只是系统中的一个节点。**

真正决定生产效果的是 Model × Harness × Context × Tools × Runtime × Evaluation。

## 3. 下一代训练数据可能越来越来自“可交互环境”

Periodic Neon 最值得关注的地方不是“1300 张 H200”，而是它让自己的实验室持续产生现实世界的新数据。

互联网数据是静态矿山；环境则可以不断产生新的问题和反馈。

对于开发者，这意味着未来最有价值的资产之一可能不是 Prompt，也不是某个模型 API，而是：

> **一个能持续生成高质量、可验证交互数据的 Environment。**
