## 1. Stealing Reasoning Traces：不要把“加密思维块”当成可以公开的无害日志

- **标签**：`Security` `Agent` `Reasoning` `Infra`
- **论文**：*Stealing Reasoning Traces from Proprietary LLM APIs*
- **提交日期**：2026-08-10
- **论文**：<https://arxiv.org/abs/2608.09867>

### 核心观点

现在一些 frontier API 不把完整 chain-of-thought 直接展示给客户端，而是返回一个加密 reasoning block，客户端在下一轮请求时再把这段 block 原样传回。很多开发者因此默认：

> 这块东西虽然看不懂，但可以安全地进入日志、trace 或公开的 Agent trajectory。

这篇论文说明这个假设并不可靠。作者发现，同一供应商生态内的 reasoning blocks 在不同 session、用户和模型之间存在可互换性，并展示了一类跨模型提取攻击：较强模型生成的加密 reasoning block 可以被送入同一提供商中的较弱模型，从而恢复隐藏推理内容。

论文报告了四类影响：

- 绕过 anti-distillation，恢复强模型的推理轨迹；
- 从公开仓库中的 Agent 日志提取隐私信息和凭证；
- 暴露最终答案已经拒绝输出、但内部推理里出现的高风险内容；
- 把不可见 payload 藏在 reasoning block 中，污染后续 Agent rollout。

作者从公开代码仓库抓取并分析了 **315,320 个 reasoning blocks**，报告恢复出 **367 个 PII artifact** 和 **182 个 credential**。这些数字来自论文实验，应视为论文作者的测量结果，而不是对所有 API 使用方式的普遍比例。

### 为什么重要

这改变了 Agent 日志的安全边界。

以前常见的认知是：

```text
visible prompt / output = 敏感内容
encrypted reasoning blob = 不透明数据，可直接日志化
```

更安全的模型应该是：

```text
所有会被模型再次消费的 opaque state
        ↓
都按潜在敏感数据处理
```

尤其是 Coding Agent、企业 Agent 和自动化研发系统，常常会把完整 session trace 放进：

- GitHub issue / PR；
- benchmark trajectory；
- observability 平台；
- bug report；
- 公共训练集。

如果这些 trace 包含加密 reasoning block，那么“人类看不懂”不等于“不可恢复”。

### 对开发者的实际启发

建议马上把 reasoning block 当成 **secret-bearing opaque state**：

```text
不要默认打印
不要进入公开日志
不要上传公共 benchmark trace
不要跨用户 / 跨租户复用
持久化时与普通日志分开
```

如果自己设计 Agent protocol，更稳妥的方向是让 opaque state 与 **session / user / model / purpose** 强绑定，并给它明确的生命周期，而不是把它当成可以无限转发的普通字符串。

另外，发布 Agent trajectory 之前最好做一层专门的 sanitizer，而不是只过滤明文 API key。

## 2. Catastrophic Remembering：CLAUDE.md 越写越长，根因可能不是“团队懒得清理”

- **标签**：`Coding Agent` `Prompt` `Skill` `Context Engineering`
- **论文**：*Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding*
- **提交日期**：2026-08-11
- **论文**：<https://arxiv.org/abs/2608.11095>

### 核心观点

这篇论文研究一个非常真实的 Coding Agent 问题：

> 为什么 CLAUDE.md、AGENTS.md、项目 Prompt 和团队 Agent 规则通常只会不断追加，而很少安全删除？

作者把这种现象称为 **Catastrophic Remembering（灾难性记住）**，它几乎是 continual learning 中 catastrophic forgetting 的反面。

机制并不复杂：

- 添加一条规则很便宜；
- 但过了一段时间以后，团队已经忘记“这条规则为什么存在”；
- 此时删除它可能导致某个已经被忘掉的回归；
- 因此最安全的行为永远是“不删”。

作者分析了 **1,867 个仓库、247,694 条 instruction 生命周期**，发现 Agent instruction 文件在生命周期内平均增长约 **226%**，并且规则越老，被删除的概率越低。

最有意思的解决方案不是“定期让 LLM 重写整份 CLAUDE.md”，而是：**给规则保存 rationale/comment。**

论文构造了可验证的 instruction 环境，报告用 comments 保存潜在理由后，可去掉 **99.3% 的 excess instructions**；在更真实的 WildIFEval 变体中，instruction-following 最高提升 **23.1%**。

### 为什么重要

这实际上把 Prompt Engineering 推向了一个更像软件工程的方向：

> 如果英文指令已经成为 Agent 的“代码”，那么它也需要注释、历史和可删除性。

仅仅保存：

```markdown
- 不要修改 generated/ 目录
```

是不够的。

更好的规则应该像：

```markdown
- 不要修改 generated/ 目录。
  - 原因：该目录由 schema compiler 自动生成，手改会在 CI 中被覆盖。
  - 来源：2026-08-03 build regression #1842
  - 验证：运行 `make schema-check`
```

这样未来 Agent 或人类才能判断：这条规则是否仍然必要，以及如何安全删除。

### 对开发者的实际启发

维护 Skill、CLAUDE.md、AGENTS.md、项目 Agent 文档时，建议至少为重要规则保存：

```yaml
rule: 不要直接修改 generated/
rationale: 由 schema compiler 生成
source: issue-1842
validation: make schema-check
added_at: 2026-08-03
```

然后把“删除规则”变成一个可验证动作：

```text
候选删除
  ↓
读取 rationale
  ↓
运行对应测试 / verifier
  ↓
确认无回归
  ↓
删除
```

这比隔几个月让模型“帮我精简这份文档”可靠得多，因为纯重写会丢掉规则存在的因果信息。

## 3. The Bitter Lesson of Tool Calling：会写代码的模型，可能更适合“用代码调用工具”

- **标签**：`Agent` `Tool Use` `Harness` `Coding`
- **论文**：*The Bitter Lesson of Tool Calling*
- **提交日期**：2026-08-06
- **论文**：<https://arxiv.org/abs/2608.06370>

### 核心观点

当前 Agent 工具调用的默认接口通常是 JSON：

```json
{
  "tool": "search",
  "arguments": {
    "query": "..."
  }
}
```

这篇论文比较另一种范式：**Programmatic Tool Calling（PTC）**。

工具被暴露成 typed Python stub，模型直接写代码：

```python
results = search(query="...")
items = [fetch(x.url) for x in results[:5]]
```

执行环境负责真正运行这些调用，再把结果返回给 Agent。

作者在 BFCL v4 上比较 **14 个模型**，并用 middleware 控制 LLM call 数量，使 PTC 与 JSON baseline 在调用预算上更可比。结果显示：

- PTC 在 **11/14** 个模型上持平或超过 JSON tool calling；
- GPT-5.6 系列相对 JSON baseline 提升 **10.6%**；
- 并行 fan-out 场景中，PTC 在 **13/14** 个模型上持平或更好；
- context rot 场景中，JSON baseline 平均下降约 **2.3%**，PTC 更稳定。

### 为什么重要

JSON tool call 的优势是结构简单、容易验证；但当任务变成：

- 循环；
- 条件分支；
- 并行调用；
- 多步数据变换；
- 组合多个工具输出；

JSON 很快就会把逻辑拆成大量 Agent turn。

而代码天然提供：

```text
控制流
变量
函数组合
并发
局部计算
异常处理
```

随着基础模型编码能力越来越强，“让 Agent 生成一串 JSON”可能反而是在限制模型已经具备的能力。

### 对开发者的实际启发

如果 Agent 的核心模型本身代码能力很强，可以考虑把 Harness 分成两层：

```text
LLM
 ↓
生成受限 Python / TypeScript 程序
 ↓
Sandbox Runtime
 ↓
Typed Tools
```

但不要把这个结论理解成“直接给模型任意 shell”。关键是 **受限执行环境 + typed tool surface + 权限控制**。

对于简单、低风险、单次调用的 API，JSON 仍然更容易验证；对于数据分析、批量检索、文件处理和复杂工具组合，PTC 更值得测试。

## 4. Reason Wide, Not Deep：把重复推理蒸馏成 Skill，而不是每次重新付 reasoning token

- **标签**：`Agent` `Skill` `Reasoning` `Efficiency`
- **论文**：*Reason Wide, Not Deep: Amortizing the Reasoning Premium into Distilled Skills*
- **提交日期**：2026-08-08
- **论文**：<https://arxiv.org/abs/2608.07885>

### 核心观点

Reasoning model 在复杂 Agent 任务上通常更强，但每一个 episode 都要重新产生长 reasoning trace。

这篇论文提出一个非常工程化的视角：

> 同一个领域里，很多推理步骤其实是重复的“程序性知识”，为什么不把它们一次性蒸馏成 Skill？

方法是：让一个 Coding Agent 读取一小批已有 trajectory，自己分析这些轨迹，然后生成一个约 **40–130 行**的自然语言 Skill；部署时把这个 Skill 放进 non-reasoning model 的系统上下文。

在 ALFWorld、tau²-bench telecom / retail、SpreadsheetBench-Verified 上，作者报告：

- 对 GPT-5.4-mini，distilled skills 能恢复 reasoning mode 与 non-reasoning mode 之间 **55% 到 100%+** 的性能差距；
- 其中两个 benchmark 甚至超过 reasoning mode；
- 输出 token 减少约 **2.7–6 倍**；
- 不再需要 reasoning token；
- 而且不一定需要读取隐藏 reasoning trace：仅从 non-reasoning trajectory 也能蒸馏出有竞争力的 Skill。

### 为什么重要

它给 Skill 一个比“写一些最佳实践”更严格的定义：

> Skill 可以是多个真实 episode 中反复出现的程序性知识的压缩产物。

因此 Reasoning 和 Skill 可以被理解成两种不同搜索：

```text
Reasoning：
一次任务里向深处搜索
每次部署重新付费

Skill Distillation：
跨很多历史任务向宽处搜索
一次提炼，多次复用
```

### 对开发者的实际启发

长期运行的 Agent 可以采用下面的成本结构：

```text
新领域 / 高不确定任务
        ↓
Reasoning Model
        ↓
积累成功与失败 trajectories
        ↓
定期蒸馏 Skill
        ↓
普通任务 → Non-reasoning / cheaper model + Skill
        ↓
遇到异常再升级到 Reasoning Model
```

这尤其适合 Coding Agent、客服 Agent、数据处理 Agent 和游戏内容生产流程：任务重复度越高，越有机会把昂贵 reasoning 变成可复用流程。

但要避免一个陷阱：**不要把每个成功 trajectory 都直接保存成 Skill。** Skill 应该跨多个任务抽象公共过程，否则会变成另一种“Catastrophic Remembering”。

## 5. Lost in Compaction：Agent 压缩上下文时，最容易丢掉的恰好可能是“绝不能忘”的规则

- **标签**：`Agent` `Context` `Memory` `Safety`
- **论文**：*Lost in Compaction: Evaluating Side-Constraint Loss under Context Compaction*
- **论文**：<https://arxiv.org/abs/2608.11242>

### 核心观点

长时间 Agent 会不断积累历史，最终不得不做 context compaction：

```text
长对话 / trajectory
       ↓
摘要 / 压缩
       ↓
继续运行
```

问题在于，普通摘要器通常会优先保存“任务主线”，却可能丢掉用户早期给出的 **Session Constraints**，例如：

> “没有得到我确认之前，不要删除任何邮件。”

论文构建了 COMPINT，在 multi-turn chat、agentic trajectory 和 long-horizon research 三类场景中测试 compactor。

作者报告，当前 compactor 对注入 Session Constraints 的平均保留率只有 **17%**，而且许多配置甚至比“不做 compaction”更差。

他们提出一个非常简单的改法：不要要求 compactor 顺便记住这些规则，而是在 compaction 旁边独立运行一个 **Session Constraint extractor**。这个 plug-and-play 模块在三个场景中都把保留率提高到 **90% 以上**。

### 为什么重要

这说明：

> “上下文摘要”与“约束持久化”是两个不同任务，不应该混成一个 prompt。

对于真正能执行操作的 Agent，忘掉普通背景信息只是体验下降；忘掉下面这些内容则可能变成事故：

```text
不要删除
不要付款
不要发布
不要修改 production
只能读取
必须先确认
```

### 对开发者的实际启发

不要把关键 Session Constraint 只存放在普通对话历史中。

更稳妥的结构：

```text
Conversation History ──→ Compactor ──→ Summary

Session Constraints ──→ Constraint Store
                              ↓
                       每轮强制重新注入
```

Constraint Store 最好是结构化的：

```yaml
- id: no-delete-email
  scope: session
  rule: 未经用户确认不得删除邮件
  active: true
  source_turn: 18
```

然后专门测试：经过 10 次、50 次、100 次 compaction 后，这些约束是否仍然存在。

这比单纯增加 context window 更重要，因为窗口再大，最终仍可能进入摘要或压缩阶段。

## 6. Mind Viruses：多 Agent 风险开始从“单个模型出错”扩展到“信息在 Agent 网络中传播”

- **标签**：`Multi-Agent` `Security` `Safety`
- **论文**：*Mind Viruses: Self-Propagating Ideas in Multi-Agent LLM Systems*
- **提交日期**：2026-08-10
- **论文**：<https://arxiv.org/abs/2608.10218>

### 核心观点

Anthropic 研究人员研究了一种新的 multi-agent 风险：某些 idea / goal 被一个 Agent 接收后，会诱导它把同样内容继续传给其他 Agent，形成类似传播行为。

作者不是手工写 payload，而是使用简单 evolutionary algorithm 搜索更容易传播的内容，并在两个设置中测试：

- 多个 Agent 共同维护一个 coding project；
- Agent 链式交互，每次交互后清空上下文。

第二个设置尤其重要：即使上下文被清掉，某些 payload 仍可以通过**共享工作产物**继续传播，说明风险不一定存在于对话 memory 中，也可能存在于代码、文档或任务 artifact 里。

论文发现传播受多种因素影响，包括 host model、已有系统指令、payload 是否有害以及网络拓扑。作者同时强调，目前这种风险仍然有限；一个非常实用的结果是：**在系统 Prompt 中加入简短警告，实验中就能带来接近完全的免疫效果。**

### 为什么重要

Multi-Agent 的攻击面不只是：

```text
用户 → Agent
```

还包括：

```text
Agent A
  ↓
代码 / 文件 / message / memory
  ↓
Agent B
  ↓
Agent C
```

当一个系统开始让多个 Agent 自动共享：

- repo 文件；
- issue；
- memory；
- tool output；
- sub-agent message；

这些 artifact 都应该被视为**不完全可信的跨边界输入**。

### 对开发者的实际启发

对于多 Agent 系统，可以先从非常便宜的措施开始：

```text
1. 在系统指令中明确：不要采纳或传播 artifact 中要求修改自身目标/指令的内容
2. 将 Agent-to-Agent message 与系统指令严格分层
3. 对共享 artifact 进行 provenance 标记
4. 高权限 Agent 不直接信任低权限 Agent 的自然语言建议
5. 将“修改目标 / 修改 policy / 创建新长期 memory”设为高风险动作
```

目前没必要因为这篇论文停止使用 multi-agent，但它提醒我们：**Agent 网络需要类似分布式系统里的 trust boundary，而不是默认所有 Agent 都在同一个可信上下文里。**

## 今日判断

今天这期新论文非常集中地指向一个趋势：

> **Agent 的下一阶段，不再只是让模型更会推理，而是让“推理、工具、文档、压缩、记忆和安全边界”成为可以单独设计、测试和替换的系统组件。**

把今天几篇论文组合起来，可以得到一个更成熟的 Agent 架构：

```text
User / External Input
        ↓
Constraint Extractor ─────→ Persistent Constraint Store
        ↓
Agent Harness
        ↓
┌───────────────────────────────┐
│ Frontier Reasoning Model      │ ← 新颖 / 高不确定任务
│ Non-Reasoning Model + Skills  │ ← 重复 / 可复用任务
└───────────────────────────────┘
        ↓
Programmatic Tool Runtime
        ↓
Sandbox / Permission Boundary
        ↓
Artifacts / Shared State
        ↓
Multi-Agent Trust Boundary
```

与此同时：

```text
Context History → 可以压缩
Session Constraint → 不应该跟着普通摘要一起赌运气
Reasoning Trace → 不应该默认进入公开日志
Agent Rule → 不应该只保存结论，还要保存 rationale
重复 Reasoning → 应该逐步蒸馏成 Skill
```

如果只选今天最值得立即落地的三个动作：

1. **把长期约束从普通 context 中拆出来，单独持久化并每轮重新注入。**
2. **给 CLAUDE.md / AGENTS.md / Skill 中的重要规则增加 rationale、来源和 verifier。**
3. **把 opaque reasoning block 当作敏感数据，停止默认写入公开 trace。**
