## 1. NVIDIA AVO：Agent Harness 可以把同一个模型的能力“放大”到完全不同的层级

- **标签**：`Agent` `Harness` `Long-Horizon` `Evaluation`
- **发布**：NVIDIA Technical Blog，2026-08-21
- **Elvis 周报**：2026-08-22 AI Agents Weekly

### 核心观点

NVIDIA 的 **AVO（Agentic Variation Operators）** 本质上不是一个新的基础模型，而是一套长期运行 Agent 架构。它围绕模型建立了：

```text
观察当前状态
  ↓
提出下一步假设 / 计划
  ↓
修改或执行
  ↓
通过外部评分函数验证
  ↓
保留有效候选
  ↓
失败诊断 / 重试
  ↓
Persistent Memory + Supervisor
  ↓
继续下一轮
```

NVIDIA 报告，在 ARC-AGI-3 的 **25 个公共环境、183 个关卡**上，AVO + Claude Opus 5 达到 **100.00 RHAE**，共使用 6,624 次环境动作；作为对比，VISTA + Claude Opus 5 报告为 7,542 次动作，因此 AVO 在跨系统比较里少用了约 12% 动作。

更值得注意的是 NVIDIA 特别强调：ARC Prize 对 Claude Opus 5 的模型级报告约为 30%，而完整 AVO 系统能做到 100%。但这**不是严格的 controlled ablation**：两边的 reasoning setting、memory、observation representation、context management 和 execution setup 都不同，所以不能简单把“70 个百分点”全部归功于 Harness。

AVO 在更早的 GPU kernel 优化实验里也展示了同一架构的长程能力：连续运行 7 天，探索 500+ 优化方向，提交 40 个 kernel 版本；在 DGX B200 上，NVIDIA 报告其结果在测试配置中相对 cuDNN 最多快 3.5%，相对 FlashAttention-4 最多快 10.5%。

### 为什么重要

这类结果进一步说明，今后评估 AI 系统时至少要区分：

```text
Model capability
      ≠
Agent capability
      ≠
Product capability
```

一个模型在静态 benchmark 上的单轮能力，只代表它作为“认知内核”的表现；真正长时间完成任务，还取决于：

- 记忆如何保留；
- 环境反馈是否可靠；
- 失败能否恢复；
- 是否有 supervisor 检测停滞；
- 工具调用是否正确；
- context 是否会逐步腐化；
- 候选结果如何保存和回滚。

这也解释了为什么过去几周大量论文都开始单独研究 Harness，而不是继续把所有性能差异都解释成模型差异。

### 对开发者的实际启发

对于需要跑几十分钟甚至几小时的 Coding Agent，不要把“继续对话”当作唯一的长期运行机制。更可靠的是显式持久化：

```yaml
run_state:
  goal: ...
  current_hypothesis: ...
  accepted_changes: ...
  failed_attempts: ...
  test_results: ...
  next_candidates: ...
  checkpoint: ...
```

尤其值得借鉴 AVO 的两个组件：

1. **Persistent Memory**：保存实现、测试、compiler/profiler 输出和已经确认的结论，避免每次 context compaction 后重新发现同一件事；
2. **Supervisor**：不要让主 Agent 无限循环。单独设计一个轻量 monitor，看“多久没进展、是否重复失败、是否应该切换策略”。

对自动性能优化、CI 修复、UE/Unity 项目批量重构这类任务，这比单纯把 context window 加长更实际。

> 注意：AVO 的 100% 是 **ARC-AGI-3 public set**，不是 semi-private 或 fully private competition set。NVIDIA 官方也在文章末尾专门澄清了这一点。

## 2. TrueForge：Agent Harness 正在变成类似“应用服务器 / 容器 Runtime”的独立基础设施层

- **标签**：`Agent` `Harness` `Open Source` `Infra`
- **发布**：TrueFoundry，2026-08-18
- **License**：MIT

### 核心观点

TrueFoundry 开源了 **TrueForge**，定位非常明确：

> 模型负责 reasoning，Harness 负责让模型真正成为可运行的 Agent。

TrueForge 把生产 Agent 常见的外围能力放在统一 runtime 中：

- agent loop；
- MCP tools；
- git-backed `SKILL.md` skills；
- sandboxed execution；
- human approval checkpoints；
- subagents；
- context compaction / deferred tool loading；
- session persistence；
- HTTP API + TypeScript SDK；
- 可嵌入 Chat UI。

一个特别值得关注的设计是：**sandbox 被当作一个 tool，而不是让整个 Agent 永远运行在 sandbox 里。** 只有 Agent 真正需要执行代码/处理文件时才启动隔离环境，因此普通 reasoning / retrieval turn 不需要持续占用 sandbox 资源。

它同时支持本地 SQLite，也支持 Hosted 模式下的 Postgres + Redis + Docker Compose / Helm，说明目标不是简单 Demo，而是把 Harness 作为可部署 runtime。

### 为什么重要

过去很多 Agent 框架更像“写 Agent 的库”：

```text
你写 Python / TypeScript orchestration
→ 接模型
→ 接工具
→ 自己维护状态
```

TrueForge 代表另一种思路：

```text
Agent Harness = 标准运行时
你只配置：
模型 + 工具 + skill + 指令 + policy
```

这和 Web 开发从“自己处理 socket / process”演进到 application server、容器和 Kubernetes 很像：当越来越多 operational behavior 聚集到某一层，这一层最终会变成独立基础设施。

TrueFoundry 自己也明确把 Harness 称为“the runtime layer around an LLM”。

### 成本结果要怎么看

TrueFoundry 在 14 个 Enterprise-Bench 风格任务上报告：

- 同模型条件下，TrueForge 相比 Claude Managed Agents 约降低 30% 成本；
- 切换到匹配准确率的开源模型时，最高可节省约 75%。

这些数字来自厂商自己的 benchmark，适合视为**值得复现的工程信号**，而不是独立第三方结论。

更重要的不是具体 30% 或 75%，而是它说明：**Harness 自己就是成本变量。** Tool result offloading、context compaction、subagent delegation、sandbox 生命周期都会直接改变 Token 和运行费用。

### 对开发者的实际启发

如果你准备长期维护多个 Agent，不要每个项目都重新手写：

```text
while model calls tool:
    execute()
    append_result()
```

应该尽早抽出统一 Runtime，至少标准化：

```yaml
agent_runtime:
  model_provider: ...
  tool_registry: ...
  skill_registry: ...
  sandbox_provider: ...
  approval_policy: ...
  context_policy: ...
  persistence: ...
  tracing: ...
```

这样以后换模型时是配置变化，而不是重写 Agent 产品。

对团队开发尤其重要：Harness 应该能被审计和测试，因为最终决定 Agent 能访问什么、保留什么、怎么恢复、什么时候需要人类批准的，往往不是模型，而是 Runtime。

## 3. Chroma Foundation：Memory 正在从“某个 Agent 的私有记忆”升级成跨 Agent 的共享基础设施

- **标签**：`Agent Memory` `Context Engineering` `Search` `Infra`
- **状态**：Research Preview
- **发布**：2026-08-20

### 核心观点

Chroma 推出的 **Foundation**，目标不是做另一个 `memory.json`，而是建立“你和多个 Agent 共享的一层长期记忆”。公开资料显示，它首批支持从以下工作流摄取信息：

- Codex；
- Claude Code；
- Cursor；
- Slack；

并计划扩展 Notion、GitHub、Google Drive 等来源。

它底层建立在 ChromaDB 与 Chroma 的 **Context-1** agentic search model 上。Context-1 是一个基于 gpt-oss-20B 的检索子 Agent，专门做多跳搜索、query decomposition 和主动 context pruning，而不是直接生成最终答案。

Chroma 的 Context-1 技术报告里，一个值得关注的思想是：检索 Agent 会显式知道自己的 token 使用量，并通过 `prune_chunks` 主动删除不相关证据。相比基础 gpt-oss-20B，报告中的 prune accuracy 从 0.824 提升到 0.941；部署时可达到约 400–500 tok/s 的端到端生成速度。

### 为什么重要

当前 Coding Agent 最大的现实问题之一是：

```text
Claude Code 知道一部分
Cursor 知道一部分
Slack 讨论里又有一部分
下周新 Session 全忘了
```

于是每个 Agent 都反复：

- 重新读代码；
- 重新发现团队约定；
- 重新询问为什么这样设计；
- 重新踩已经踩过的坑。

Foundation 代表的方向是：**Memory 不绑定某个 Agent，而绑定用户 / 团队 / 项目。** Agent 只是来读写这层长期上下文的不同客户端。

长期看，这种设计很可能比“每个 Agent 自己维护一套 memory”更合理，因为模型和 Agent 工具更换得很快，但项目历史、架构决策和团队经验应该持续存在。

### 对开发者的实际启发

如果自己设计长期 Memory，建议不要把它做成单纯的聊天摘要集合，而是至少分三层：

```text
Raw Evidence
  - 原始对话 / commit / issue / 文档

Structured Memory
  - 决策
  - 约束
  - 已验证事实
  - 失败经验

Retrieval / Search Agent
  - 根据当前任务动态检索
  - 主动过滤噪声
  - 保留 provenance
```

尤其要保留 provenance：

```yaml
memory:
  claim: "项目统一使用 GAS 处理角色能力"
  source: "architecture-review-2026-08-18"
  author: ...
  confidence: verified
  last_checked: ...
```

否则跨 Agent 共享 Memory 很容易变成“共享幻觉库”。

另外，Context-1 的经验值得直接借鉴：**不是把所有检索结果都留下来，而是训练 / 设计检索 Agent 主动删除已经判定无关的 context。** Memory 系统真正的价值并不是“记得越多越好”，而是“在当前任务里取回正确的少量内容”。

## 4. Ornith-1.5：真正有意思的不是“开源模型接近 Opus”，而是训练循环开始自己生成下一轮训练问题

- **标签**：`Self-Improvement` `RL` `Coding Agent` `Open Models`
- **模型规模**：397B MoE、35B MoE（约 3B active）、9B Dense

### 核心观点

Ornith-1.5 把 self-improvement 从“优化解题过程”扩展成三段联合循环：

```text
Task Generator
  ↓
生成比当前能力略难的新任务
  ↓
Scaffold Generator
  ↓
为任务设计工具 / 指令 / 分解 / orchestration
  ↓
Solution Rollout
  ↓
执行并得到 reward
  ↓
GRPO / RL 更新
  ↓
更强模型生成更难任务
```

也就是说，它不是只优化“答案”，而是同时优化：

1. **训练什么问题**；
2. **用什么 Agent Scaffold 来解决问题**；
3. **最终怎么执行**。

任务 reward 由三类信号组成：

- **Validity**：任务和 evaluator 必须真的有效；
- **Frontier Difficulty**：成功率不能太高也不能接近 0，作者把目标 frontier success rate 设为 `p*=0.2`；
- **Novelty**：避免不断生成同一类轻微变体。

随着模型变强，旧任务成功率升高，difficulty reward 自然下降，从而迫使 task generator 继续把 curriculum 往更难方向推。

### 结果怎么看

Ornith 官方报告：

- 397B：Terminal-Bench 2.1 = 86.1，DeepSWE = 56.0；
- 35B-A3B：Claude Code harness 下 Terminal-Bench 2.1 = 68.5，SWE-bench Verified = 79.0；
- 9B：Claude Code harness 下 Terminal-Bench 2.1 = 47.0，SWE-bench Verified = 70.6。

旗舰 397B 在部分 coding / agentic benchmark 上接近 Claude Opus 4.8，但这仍然是官方发布结果，且不同 benchmark 的 harness、context window 和 judge 设置差异很大，不能把“接近 Opus”泛化成所有实际任务都同等能力。

### 为什么重要

过去“self-improving agent”经常只是：

```text
做任务
→ 看失败
→ 改 Prompt / Skill
→ 再做一次
```

Ornith-1.5 更进一步：**训练数据分布本身也在 Agent loop 里演化。**

这接近一种自动 curriculum learning：模型专门寻找“自己现在刚好不会、但又不是完全不可解”的任务。

如果这种机制变可靠，未来 post-training 的一个核心资产可能不再只是人工整理的 dataset，而是：

> 一个能持续生成有效、可验证、处于能力边界附近任务的训练环境。

### 对开发者的实际启发

即使不训练大模型，也可以把这个思想应用到 Agent Evals：

不要一直维护静态测试集，而是让一个“Challenge Generator”从历史失败中不断生成新案例：

```text
生产 Trace
  ↓
聚类失败模式
  ↓
生成更难但可验证的变体
  ↓
加入 regression eval
  ↓
Agent 修复
  ↓
继续寻找边界
```

关键是不能只奖励“难”。必须像 Ornith 一样先做 validity gate，否则 evaluator 错了、任务不可解，也会制造虚假的“高难度”。

这对于 Coding Agent、自动 UI 测试、游戏 AI 测试尤其有价值：让系统持续围绕真实失败生成新的 regression case，而不是只跑固定 benchmark。

## 5. LEGO-RL：Coding Agent 的 RL 开始直接进入真实 Harness，而不是训练一个“像 Claude Code 的简化模拟器”

- **标签**：`RL` `Coding Agent` `Harness` `Training Infrastructure`
- **论文**：*LEGO-RL: Harness-Native Reinforcement Learning for Coding Agents*
- **arXiv**：2608.17393
- **提交日期**：2026-08-18

### 核心观点

Coding Agent 的强化学习长期有一个结构性问题：

```text
训练环境 ≠ 实际部署 Harness
```

真实 Claude Code / OpenHands / OpenCode 会做很多训练框架不喜欢的事情：

- context compaction；
- re-serialization；
- 工具调用；
- sandbox 重启；
- 长时间执行；
- 环境崩溃；
- 中途产生大量非模型 token。

Policy-gradient RL 又要求训练器知道模型到底生成了哪些 token，并准确重算 log probability。

LEGO-RL 的目标就是：**不修改原生 Agent Harness 的内部控制流，也能在 Harness 内做 scalable policy-gradient optimization。**

它主要依赖三个组件：

1. **In-process LLM proxy**：截获 raw generation stream，保持 rollout token 与 trainer 重算 log-prob 对齐，即使 Harness 后续做了 compaction / re-serialization；
2. **Sandbox orchestration + 防 reward hacking**：把环境执行稳定性纳入训练基础设施；
3. **训练可观测性**：plugin + Live UI 检查 trajectory，避免 RL 训练变成黑盒。

### 实验结果

作者用 Qwen3.5-35B-A3B + GSPO，在三个真实 Coding Harness 里训练，并报告 SWE-bench Verified：

```text
OpenHands SDK   64.0% → 70.4%
Claude Code     62.4% → 68.2%
OpenCode        57.2% → 66.6%
```

同时 rollout 与 training probability 的相关性保持在 **0.99 以上**。

### 为什么重要

最近我们已经看到越来越多证据说明：**模型会对 Harness 产生适配。**

那么一个很自然的问题就是：

> 为什么 post-training 还要在一个简化的、人造的 Agent loop 里完成？

如果最终产品运行在 Claude Code / OpenHands / 自定义 Harness 中，那么训练时直接面对真实 Harness 才能学习：

- 它如何压缩 context；
- 它如何反馈 tool error；
- 它有哪些默认行为；
- 它如何组织文件；
- 什么时候应该停止；
- 哪些行为会触发 sandbox / evaluator。

这很可能把未来模型训练与 Agent Infra 更紧密地绑在一起。

### 对开发者的实际启发

即使你不做 RL，也应该尽量让：

```text
Eval Harness
≈ Production Harness
```

不要在一个极简 benchmark runner 上验证通过，就认为线上 Agent 一定会工作。

至少应复现线上关键机制：

- 相同 system prompt；
- 相同 tool schemas；
- 相同 compaction 策略；
- 相同 sandbox；
- 相同 retry / timeout；
- 相同 approval policy；
- 相同输出 validator。

否则你测到的是“模型在实验框架里的能力”，不是“产品 Agent 的能力”。

对于未来真正做 Agent post-training 的团队，LEGO-RL 提供的方向也很值得关注：**Harness 逐渐会从 inference-only 软件，变成训练基础设施的一部分。**

## 今日判断：下一阶段的 Agent 竞争，可能是“模型 × Harness × Memory × Training Loop”的联合优化

把今天五项放在一起：

```text
Ornith-1.5
  → 模型会自己生成训练任务和 scaffold

LEGO-RL
  → 模型直接在真实 Harness 里训练

TrueForge
  → Harness 本身成为独立可替换 runtime

Chroma Foundation
  → Memory 从 Agent 内部迁移成跨 Agent 基础设施

NVIDIA AVO
  → Harness + Memory + Supervisor 可以显著改变完整 Agent 的长期表现
```

这意味着以后讨论“哪个模型最好”会越来越不够。

更现实的评价单位应该是：

```text
Agent System
=
Model
× Harness
× Context / Memory
× Tools
× Runtime
× Verifier
× Training / Eval Environment
```

其中任何一个乘数接近 0，产品就会失败。

### 对开发者最值得立刻采用的三条原则

1. **把模型和 Harness 分开版本化。**
   不要只记录 `model=gpt-x`，还要记录 harness、toolset、context policy、stop condition。

2. **让 Memory 独立于单个 Agent。**
   原始证据、项目决策和验证过的经验应该能跨模型、跨工具复用。

3. **让 Eval 尽可能接近真实 Runtime。**
   如果生产里有 compaction、sandbox、approval、subagent，评测里也应该存在，否则结果会过度乐观。
