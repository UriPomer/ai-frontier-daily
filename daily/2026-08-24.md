## 1. Self-Improving Agent 的最大问题：你看到的提升，可能只是任务顺序制造出来的

- **标签**：`Agent` `Memory` `Evaluation` `Reliability`
- **论文**：*On the Fragility of Self-Improving Agents: Variance, Task Order, and Underspecification*
- **提交日期**：2026-08-18

### 核心观点

这篇论文重新评估了两类典型的“记忆驱动自我改进”方法：

- **Agent Workflow Memory（AWM）**：从成功轨迹里总结可复用 workflow；
- **ReasoningBank（RBank）**：从成功和失败轨迹中提炼 reasoning insight，再按任务检索相关记忆。

作者在 WebArena、VisualWebArena 和 SCUBA 上做多次重复实验后发现两个很关键的问题。

第一，**自我改进环路会放大方差**。例如在 WebArena GitLab 子集上，无记忆 baseline 三次运行的最好/最差差距约为 **4.4 个百分点**，加入 ReasoningBank 后扩大到 **7.8 个百分点**。

第二，**提升高度依赖任务顺序**。默认 benchmark 顺序本身带有一种隐含的“由易到难 curriculum”。在默认顺序下，ReasoningBank 相对 baseline 平均提升约 **+1.5%**；随机打乱后，反而出现约 **-4.5%** 的退化。论文总结，在测试的 8 种 shuffled 设置里有 6 种出现明显下降。

作者进一步发现，一个根因是 **underspecification（信息不足）**：记忆生成器并不知道真实环境限制，于是会写下“调用 API”之类在 browser-only 环境中根本无法执行的经验；模糊任务也会被错误解释，并把这种误解固化成长期记忆。

加入更详细的环境反馈、rubric 与环境约束后，只能补回约 **31%** 的 shuffled-order 性能损失，说明问题还没有被完全解释。

### 为什么重要

这直接挑战了一个现在很流行的产品叙事：

> Agent 做得越久 → memory 越多 → 能力自然越来越强。

现实更可能是：

```text
经验越多
  ↓
正确经验 + 错误经验同时积累
  ↓
检索误差 / 环境变化 / 错误归因
  ↓
某些任务变强，另一些任务变差
```

所以“长期记忆”不能只看累计成功率，而必须测试：

- 多随机种子；
- 多任务顺序；
- stale memory；
- 环境变化；
- 错误经验是否能够被撤销。

### 对开发者的实际启发

如果要做长期 Coding Agent、个人助手或游戏 NPC，不建议把每次“成功总结”永久写入 memory。更稳妥的是给记忆增加来源和可信度：

```yaml
memory:
  claim: "..."
  source_task: "..."
  environment_version: "..."
  evidence: "..."
  confidence: 0.78
  last_verified_at: "..."
  invalidated_by: null
```

并且评测时至少加入一个 **shuffle test**：把同一组任务随机排序重新跑。如果所谓“自我改进”只在固定 curriculum 下成立，它还不能算真正稳定的持续学习。

## 2. dots3-note + TEMPO：长程 Agent 的 RL 不应该等几十小时才收到一次奖励

- **标签**：`Agent` `RL` `Multimodal` `Long-Horizon`
- **模型**：dots3-note Preview
- **团队**：小红书 dots studio
- **状态**：开放权重 Preview，Apache 2.0

### 核心技术

官方公开的 dots3-note Preview 采用多模态 MoE：

- **280B 总参数 / 16B 激活参数**；
- 512K context；
- 256 routed experts + 1 shared expert，Top-8；
- 13 层 DSA + 33 层 SWA；
- 7B 总参数、1.2B 激活的 MoE Vision Encoder；
- 800M Audio Encoder；
- 支持文本、图像、视频和音频输入；
- 官方给出 SGLang / vLLM 部署路径，FP8 推荐单机 8 卡。

但真正值得关注的是它针对长程 Agent RL 提出的 **TEMPO（Test-Time-Scaled Value Estimation with Macro-Step Policy Optimization）**。

普通 GRPO 在超长任务中有一个很直接的问题：

```text
Agent 连续运行 10~40 小时
        ↓
任务终于结束
        ↓
才得到 final reward
        ↓
再做一次梯度更新
```

这样训练信号极慢，而且几十小时之前的某个决策到底贡献了多少几乎无法归因。

TEMPO 的思路是把完整轨迹切成多个 **macro-step**。每个 macro-step 结束时，同一个模型从 actor 临时切换成 generative critic，通过更长的 test-time reasoning 评估当前状态“未来还可能拿到多少 reward”。于是无需等整条轨迹结束，就可以用：

```text
当前 macro-step 的环境奖励
+
Critic 对后续剩余回报的估计
```

形成训练信号并更新 actor。

### 为什么重要

这是 long-horizon Agent 训练的核心基础问题之一。

如果一个真实 coding / research / game-playing Agent 的 rollout 本身就需要数小时，传统“完整 rollout → final reward → 更新”的 RL 流程物理上就很难扩展。

TEMPO 代表的方向是：**把 Agent 的自我评估能力本身训练成 value estimator**，而不是必须维护一个只能做固定前向计算的独立 value head。

### 对开发者的实际启发

即使不训练模型，这个思路也能直接应用到 Agent Runtime。

不要只在最终结果检查一次：

```text
计划 → 连续执行 100 步 → 最终验证
```

可以改成：

```text
计划
 ↓
执行 5~10 个关键动作
 ↓
Checkpoint
 ↓
独立 Critic / Verifier 判断：
- 当前状态是否更接近目标？
- 是否正在重复失败？
- 是否需要回滚？
- 当前假设是否仍成立？
 ↓
继续下一 macro-step
```

对于自动修 Bug、UE/Unity 大规模重构、长时间数据处理任务，这类阶段性 value/checkpoint 往往比“让模型一直思考直到做完”可靠。

## 3. DeepSeek-V4-Flash-Vision-Exp：低成本 Agent 模型开始原生吃截图

- **标签**：`Agent` `Multimodal` `Model` `API`
- **发布日期**：2026-08-21
- **状态**：Experimental API

### 核心更新

DeepSeek 在 8 月 21 日 API changelog 中正式加入：

```text
model = "deepseek-v4-flash-vision-exp"
```

这是 V4-Flash 系列的实验性视觉版本。官方明确表示：

- 纯文本 Agent、推理和知识能力与正式版 V4-Flash 基本持平；
- 需要视觉理解的 Agent benchmark 显著提升；
- 官方称其 multimodal-agent 能力接近 Opus-4.8。

DeepSeek 同时给出一组官方 benchmark：

- Terminal Bench 2.1：83.9
- NL2Repo：57.7
- DeepSWE：59.3
- DSBench-Hard：63.6
- AutomationBench Public：25.7
- ApexBench Pass@1：36.5
- Agents' Last Exam：27.3
- Chartography：64.3
- ZeroBench Pass@5：35.0

需要特别注意：这些都是 **DeepSeek 官方自报数字**，其中 Code Agent 测试使用 DeepSeek Harness minimal mode、max effort、top-p 0.95、temperature 1.0。独立第三方评测仍需要跟进。

### 为什么重要

低价 Coding Agent 过去一个现实缺口是视觉：

```text
代码模型很便宜
 ↓
遇到 UI 截图 / 浏览器页面 / 图表
 ↓
必须路由到另一个昂贵 Vision Model
 ↓
状态、上下文和工具链变复杂
```

如果 Flash 级模型可以直接接图像，那么浏览器 Agent、UI 自动化、游戏测试和视觉 Debug 的路由成本会明显下降。

这类模型尤其适合：

- Playwright 截图检查；
- 游戏 UI / HUD 自动测试；
- 网页 Agent；
- Dashboard / 图表读取；
- OCR 后进一步 reasoning；
- 低成本多模态 sub-agent。

### 对开发者的实际启发

多模态 Agent 不一定需要从头到尾都用昂贵旗舰模型。可以使用：

```text
Flash Vision
  ↓
识别 UI / 截图 / 图表 / 页面状态
  ↓
Structured Observation
  ↓
主 Coding / Planning Agent
```

或者直接让低成本 Vision Agent 完成简单的 UI 操作，只在复杂规划阶段升级到更强模型。

关键是把 **视觉理解成本也纳入 Agent routing**，而不是默认所有截图都走最高价模型。

## 4. Cursor Continuity：Git Hosting 正在被 Agent 工作负载逼着重新设计

- **标签**：`Infra` `Coding Agent` `Git` `Distributed Systems`
- **文章**：*Git at any scale*
- **发布日期**：2026-08-18

### 核心技术

Cursor 在 Origin 代码托管平台背后构建了新的 Git storage system：**Continuity**。

传统 Git hosting 很依赖 packfile + 本地 filesystem。Cursor 认为这在两个新场景下开始出现严重扩展问题：

1. 企业 monorepo 越来越大，CI 和 Agent 会产生大量并发 clone/fetch；
2. Agent 会不断创建大量短生命周期 repository / branch / workspace，让“每个 repo 固定多副本”越来越浪费。

Continuity 的核心思路是：

```text
S3-compatible object storage
        = Source of Truth

本地 Git repo
        = Warm Cache
```

每次 push 先写成 **Write-Ahead Log（WAL）**：

```text
Push
 ↓
Packfile 写本地 + 上传 S3
 ↓
WAL entry 完整持久化
 ↓
准备本地 ref transaction
 ↓
WAL index 发布
 ↓
才向客户端 ACK
```

因此服务器节点本身可以近似无状态。某个节点没有 repo，就从 WAL materialize；平时使用 rendezvous hashing 让 repo 保持在一组预期节点上，但这个 mapping 并不是 correctness 的来源。

Cursor 报告，使用 S3 Standard 时 Continuity 可以在持续 compaction 和 replication 情况下达到约 **120 pushes/s**；使用 S3 Express One Zone 时可超过 **300 pushes/s**，瓶颈转向 Git 自身的本地 compaction。

### 为什么重要

这不只是 Git 基础设施故事，它直接反映 **Coding Agent 正在改变开发平台的负载模型**。

以前 Git Server 的典型负载是：

```text
人类开发者
几十分钟一次 push
CI 偶尔 clone
```

Agent 工作负载可能变成：

```text
几十 / 几百 Agent
持续 branch / commit / push
并行 CI
频繁 sandbox clone
大量短生命周期 repo
```

也就是说，AI Coding 的瓶颈开始从模型侧扩散到代码托管、仓库复制、CI、artifact、cache 和 sandbox 基础设施。

### 对开发者的实际启发

如果在做 Agent-driven CI / Coding Platform，不要假设 Git 操作成本永远可以忽略。

值得提前监控：

```yaml
git_metrics:
  clone_rate: ...
  fetch_rate: ...
  push_rate: ...
  repo_materialization_latency: ...
  checkout_size: ...
  short_lived_repo_count: ...
  ci_fanout: ...
```

对于自己的项目，也可以减少 Agent 每次任务都做完整 clone：优先使用 shallow clone、workspace cache、bare repo cache、worktree，或者让多个 sandbox 共享只读 object store。

## 今日判断

今天这四项可以拼成一条非常完整的 Agent 工程链路：

```text
长期 Agent
  ↓
Memory / Self-improvement
  ↓
必须做更严格的 shuffle + variance 评测
  ↓
任务越来越长
  ↓
需要 macro-step / checkpoint / critic
  ↓
Agent 越来越多模态
  ↓
需要廉价视觉模型进入工具循环
  ↓
Agent 数量继续扩大
  ↓
Git / CI / storage 也要按机器工作负载重构
```

一个值得持续观察的趋势是：**Agent 的“可用性”越来越不由单个模型 benchmark 决定。**

真正的系统能力来自：

- 模型；
- Harness；
- Memory；
- Verifier；
- RL / Training Loop；
- Multimodal Routing；
- Runtime；
- Git / CI / Storage Infrastructure。

这意味着对开发者而言，未来最有价值的能力之一会是：**能把 Agent 当成分布式软件系统来设计、测量和调试，而不是把它当成一个 Prompt。**
