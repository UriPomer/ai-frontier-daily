## 核心进展

### 1. Shieldstral：安全模型开始变成 Agent 栈里的独立“小模型组件”

- **标签**：`Agent` `Safety` `Multimodal`
- **论文**：*Shieldstral*
- **核心技术**：Mistral 团队提出一个约 3B 参数的、可按策略适配的多模态安全分类器。它把不同内容审核任务统一改写成二元问答问题，使原本标签体系不同的安全数据可以被放进同一训练框架。论文披露的数据构建规模约为 5,410 万样本，并强调模型不仅做文本安全分类，还覆盖多模态输入。
- **为什么重要**：过去很多 Agent 把安全完全交给主模型自己“判断要不要做”，但主模型同时承担规划、工具调用、上下文压缩和执行，很容易出现职责耦合。Shieldstral 代表另一条更工程化的路线：**把安全检查拆成一个独立、便宜、可版本化、可替换的策略模型**。
- **开发者启发**：对有工具权限的 Agent，可以在工具调用前后各放一道独立 Safety Gate，而不是只依赖系统 Prompt。

```text
用户请求 / 外部内容
      ↓
Safety Classifier
      ↓
主 Agent 规划
      ↓
Tool Call
      ↓
Safety Classifier / Policy Check
      ↓
真正执行
```

对游戏开发也很实用：如果以后做带联网、UGC、截图理解或自动操作能力的 NPC/编辑器 Agent，可以让安全分类器独立检查玩家上传内容、网页内容和即将执行的高风险动作。这样策略升级时，不必重新训练或替换整个主模型。

- **来源**：<https://arxiv.org/abs/2607.25857>

### 2. Cloudflare：长期 Agent 不应该被当成“一个一直运行的进程”

- **标签**：`Agent` `Infra` `Runtime`
- **核心技术**：Cloudflare 的 Agents 文档把长期 Agent 定义成一个**持续存在的身份（durable identity）**，而不是永久占着 CPU 的进程。Agent 可以休眠、被请求或定时任务唤醒；状态、SQLite 数据、调度任务和执行检查点持久保存，但内存变量、普通 timer 和未完成的本地闭包不保证存活。
- **关键机制**：
  - `runFiber()`：适合几分钟级、需要在崩溃后恢复的工作；
  - `startFiber()`：适合需要先“可靠接单”，再异步执行、查询状态、取消或去重的任务；
  - Workflows：适合更重的多步骤后台任务、自动重试和等待外部事件；
  - Sub-agents：每个子 Agent 拥有独立状态和 SQLite，由父 Agent 负责协调。
- **为什么重要**：很多 Demo Agent 的结构还是 `while(true) + LLM + tools`，但真正运行几天、几周后，会遇到重启、模型超时、外部 API 慢、人工审批隔夜、部署升级等问题。此时“持续进程”思维很脆弱，而“身份 + 持久状态 + 可恢复执行”更接近真正的生产系统。
- **开发者启发**：设计长期 Agent 时，优先保存**目标、任务队列、检查点和不可重复副作用的执行记录**，而不是依赖内存里的当前调用栈。关键工具调用需要幂等键（idempotency key），恢复后不能重复扣款、重复发消息或重复提交代码。

一个更稳妥的长期 Agent 结构可以是：

```text
Durable Agent Identity
├─ Persistent State / SQL
├─ Task Queue
├─ Checkpoints
├─ Schedules
└─ Execution Ledger
       ↓
   唤醒后继续运行
```

对于长期游戏世界 Agent 或自动开发 Agent，这种设计比“维持一个超长上下文会话”可靠得多。

- **来源**：
  - <https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/>
  - <https://developers.cloudflare.com/agents/runtime/execution/durable-execution/>
  - <https://developers.cloudflare.com/agents/harnesses/>

### 3. OpenRouter Ori：评测模型时，Harness 本身也必须被固定和版本化

- **标签**：`Agent` `Evaluation` `Harness`
- **核心技术**：OpenRouter 官方 Skills 仓库已经提供 `spawn-ori-eval`，用于启动一个 headless Ori 评测运行；其描述中特别强调，评测会在**固定的 Harness 和模型配置**上完成任务生成、执行与评分。OpenRouter 自己的 Agent SDK 则把 Harness 拆成模型调用、工具执行、循环、输入验证、流式输出、成本跟踪与停止条件。
- **为什么重要**：这和最近几天的“Model or Harness?”、DataSpace、Prompt-Induced Waste 形成同一个结论：如果模型 A 用 20 个工具、自动重试、子 Agent 和 200K Context，而模型 B 用一个简单 while-loop，那么最终分数根本不能被解释为纯模型能力差异。
- **开发者启发**：自己的 Agent Benchmark 至少应把以下内容一起版本化：

```yaml
model: xxx
harness_version: 1.4.2
system_prompt_hash: ...
toolset_version: ...
context_policy: ...
stop_condition: ...
max_steps: 40
max_tokens: 120000
retry_policy: ...
```

尤其是你以后比较不同 Coding Agent 或做模型路由时，建议评价指标从“谁分数最高”改成：

> **在固定 Harness 下，每个成功任务花多少钱、多久、多少 Tool Call？**

这会比只看 SWE-bench 一类单点成绩更接近实际开发体验。

- **来源**：
  - <https://github.com/OpenRouterTeam/skills>
  - <https://openrouter.ai/blog/agent-sdk-with-callmodel/>

### 4. Firecrawl：文档解析正在变成 Agent Context Pipeline 的基础设施

- **标签**：`Agent` `RAG` `Infra`
- **核心技术**：8 月 8 日的 newsletter 把 Firecrawl 的文档解析工作列为值得关注的新进展。Firecrawl 官方 release notes 可验证其 `/parse` 接口已经能直接处理本地文件，并输出 LLM 可消费的 Markdown、JSON 或摘要；支持格式包括 PDF、DOCX、DOC、ODT、RTF、XLSX、XLS 和 HTML，单文件最高 50 MB。其 PDF 管线还提供 `fast`、`auto`、`ocr` 等模式，并可限制 `maxPages`。
- **为什么重要**：现实 Agent 的 Context 往往不是干净 Markdown，而是扫描 PDF、Word、Excel、报告、表格和混合版式文档。真正影响 Agent 准确率的，很多时候不是模型推理，而是**最前面的文档解析是否保留了表格结构、页码、标题层级和原始证据定位**。
- **开发者启发**：不要把“文件上传 → 整篇文本塞给 LLM”当成默认方案。更好的流程是：

```text
Document
  ↓
类型识别
  ↓
Text / OCR / Table Parser 路由
  ↓
结构化块 + 页码 + 来源
  ↓
检索 / Query-aware Filtering
  ↓
LLM
```

对扫描件使用 OCR，对原生 PDF 优先走文本解析；超长 Excel 先按 Sheet/表结构过滤；所有提取块都保留页码或单元格位置。这样后续回答错误时才能回溯到真实证据，而不是只能看一段不可追踪的摘要。

- **来源**：
  - <https://github.com/firecrawl/firecrawl/releases>
  - <https://github.com/firecrawl/firecrawl>

## 今日判断

今天这几项看起来分散：一个 Safety Model、一个 Runtime、一套 Eval Harness、一个 Document Parser，但它们其实指向同一个趋势：**Agent 产品正在从“一个大模型 + Prompt”变成真正的软件系统。**

一个越来越完整的生产 Agent 栈大致会变成：

```text
输入 / 文件 / 网页
      ↓
Parser & Context Pipeline
      ↓
Safety / Policy Layer
      ↓
Agent Harness
      ↓
Model
      ↓
Tools / Sub-agents
      ↓
Durable Runtime
      ↓
Verifier / Evaluator
```

其中任何一层都可能决定最终效果。对开发者来说，接下来真正值得积累的能力不只是 Prompt Engineering，而是**Context Engineering、Harness Engineering、Agent Runtime 和可验证评测**。
